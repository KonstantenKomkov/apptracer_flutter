# Проектные решения

Решения, которые читатель мог бы обоснованно ожидать увидеть противоположными,
вместе с аргументацией — чтобы с ней можно было спорить, а не догадываться о
ней.

## `appRunner` живёт в `Tracer.initialize`, а не в `TracerPlatform`

Запуск хост-приложения внутри охраняемой зоны устроен одинаково на всех
платформах: сама зона, цепочка обработчиков и правило «вызвать `appRunner`
ровно один раз» не меняются от платформы к платформе. Вынести `appRunner` в
интерфейс платформы означало бы обязать каждую реализацию выводить эту логику
заново — то есть получить по одной незаметной ошибке на платформу.

Поэтому `TracerPlatform.initialize` принимает только опции, а жизненный цикл
живёт в `Tracer.initialize` в пакете, обращённом к приложению. Гарантия, которая
важна вызывающей стороне, — `appRunner` выполняется ровно один раз при любом
сценарии отказа — остаётся в силе и покрыта тестами на каждую ветку.

## `TracerPlatform extends PlatformInterface`, а не интерфейс

`abstract interface class` позволил бы реализации написать `implements`, а
значит каждый новый член контракта становился бы ломающим изменением для всех
реализаций. Наследование от `PlatformInterface` с его проверкой токена — это
конвенция Flutter именно потому, что она позволяет федеративному интерфейсу
расти совместимым образом.

## `setCustomKey` ложится на `Tracer.setCustomProperty` на Android

Android SDK предлагает две похожие вещи: `setKey` (вкладка «Ключи», значение
ограничено 31 символом) и `setCustomProperty` (вкладка «Данные», значение
ограничено 128). Тридцать один символ — слишком мало для большинства того, что
вызывающая сторона реально хочет приложить: URL, идентификатор запроса, полезная
нагрузка фичефлага. Поэтому выбран `setCustomProperty`. Если поиск по ключам во
вкладке «Ключи» для вас важнее длины значения, вызывайте нативный API напрямую.

## Автоматически перехваченные ошибки по умолчанию не фатальны

Ошибка, пойманная через `FlutterError.onError`, `PlatformDispatcher.onError` или
охраняемую зону, **не завершила процесс** — именно поэтому нативные SDK её и не
видят. На Android и iOS фатальный отчёт учитывается в метрике crash-free, так
что репортить такие ошибки как фатальные значило бы сообщать о крэшах, которых
не было, и превратить метрику в измерение чего-то, кроме крэшей.

`TracerOptions.reportUnhandledErrorsAsFatal` существует для команд, осознанно
решивших иначе.

## Web, десктоп и Аврора говорят с HTTP-приёмом Tracer напрямую

JavaScript-SDK Tracer поставляется только как npm-пакет `@apptracer/sdk`, а
Flutter-сборка под web не умеет включать в себя npm-пакет. Под десктоп у
вендора SDK нет вовсе, под Аврора ОС — нативная C/C++-библиотека с системными
минидампами, до которой из Dart не дотянуться.

Поэтому `apptracer_flutter_http` шлёт события сам:
`POST sdk-api.apptracer.ru/api/crash/uploadBatch`, авторизуясь тем же
`appToken`, что и Android-плагин. Нужен только HTTP-клиент.

**До 26.08.2026 здесь стояло другое решение — протокол Sentry.** Оно было
записано без ссылки на источник, и часть его оказалась верной, а часть — нет.

Верно: Tracer действительно принимает события по протоколу Sentry, и это его
рекомендация для платформ, под которые нет их SDK — Java, Go, Python, PHP,
C/C++ под Windows, Linux и macOS. Sentry DSN выдаётся в разделе
**Настройки → Проект → API**, но только если проект заведён **через VK Cloud**.

Неверно — для web: под JavaScript у Tracer есть собственный SDK, и вендор
рекомендует именно его. DSN у обычного JS-проекта не выдаётся, а сам
`@apptracer/sdk` 2.6.9 ходит в собственный приём. Поэтому web переведён на
`/api/crash/uploadBatch`; формат восстановлен перехватом живого запроса и описан
в [web-protocol.md](web-protocol.md), пакет тогда же переименован из
`apptracer_flutter_sentry`.

**Для десктопа решение принято 27.08.2026: не поддерживаем в этом релизе.**
Ни один из двух путей туда не проверялся ни разу на живом проекте, а
документированный — Sentry SDK с DSN из VK Cloud — вдобавок требует DSN,
которого у обычного проекта нет. Пример под десктоп больше не запускается, и в
таблице платформ он помечен как неподдерживаемый. См. [status.md](status.md).

Цена решения: на web не перехватываются JavaScript-ошибки за пределами
Flutter-приложения, а на десктопе и Авроре не собираются нативные сбои —
для них нужен нативный SDK вендора.

## SDK Tracer подключены как `compileOnly` / `s.dependency` и не вендорятся

Ни один артефакт вендора не распространяется вместе с пакетом. На Android SDK
подключён как `compileOnly`, а хост-приложение добавляет настоящую зависимость
рядом с Gradle-плагином, который ему всё равно нужен; на iOS podspec объявляет
`OKTracer`, и CocoaPods забирает его из собственного spec-репозитория вендора.

Так одновременно остаются верны две вещи: пользователь получает SDK вендора
напрямую от вендора и на его условиях, а этот пакет никогда не фиксирует версию
вендорского SDK внутри чужой сборки. Цена в рантайме — плагин обязан пережить
отсутствие SDK, что он и делает, сообщая «сбор выключен» вместе с внятным
объяснением, что делать.

## Рейт-лимит на нефатальные ставится через непубличный сеттер SDK

Ожидаемое решение — попросить разработчика написать одну строчку в манифесте:
`android:name="ru.apptracer.flutter.TracerApplication"`. Пакет так и делал.
Строчка нужна была затем, что SDK читает конфигурацию только у объекта
`Application`, а плагин — не он.

Взамен пакет теперь пишет конфигурацию в `Tracer.runtimeConfigs` из
собственного `ContentProvider` с `android:initOrder="100"`, то есть раньше
провайдера самого Tracer. `Tracer.init` затирает это поле только тогда, когда
`Application` реализует `HasTracerConfiguration`; иначе оставляет, а
`CrashLoggerInternal` читает его следом, когда строит `TokenBucket` для
нефатальных. Приоритет получается ровно тот, который ожидает разработчик:
конфигурация приложения — сильнее.

Цена — один вызов `setRuntimeConfigs$tracer_commons_release`, kotlin-овского
`internal`. Аргументы за то, что цена приемлемая:

* Без него теряются ошибки, и теряются молча — жёсткий потолок Tracer в **8
  нефатальных за сессию** первым встречает как раз то приложение, которое
  ничего не настраивало. Строчку в манифесте пропускают ровно те, кто про
  потолок не знает.
* Отказ безопасен и заметен: сеттер зовётся один раз при старте процесса, из
  провайдера, под `catch (Throwable)`. Если вендор его уберёт — придёт
  `NoSuchMethodError`, интеграция вернётся к сегодняшнему поведению, а
  страховка (`TracerApplication` в манифесте) остаётся в пакете и в README.
* Вызов прямой, не через рефлексию: R8 переименует члены SDK вместе с местом
  вызова, а имя, найденное по строке, сломалось бы именно в минифицированном
  релизе. Файл — `TracerAutoConfig.java`, а не `.kt`, потому что имя с
  `$module` Kotlin выговорить не может.

Проверено на устройстве (Android, 2026-08-28), три сборки: без своего
`Application` бакет нефатальных стал `capacity=10`,
`refillIntervalNs=360000000000` — 10 в час вместо `oneShot(8)`; с `TracerHostApplication` примера — снова 8, то есть
конфигурация приложения не затирается; в минифицированном release-APK вызов
проходит. В сборке без SDK Tracer провайдер пишет одну строку в лог и
приложение стартует нормально.

Штатной точки расширения для этого у SDK нет: `ru.ok.tracer.startup.Initializer`
подключается через `meta-data`, но порядок инициализаторов задаётся перебором
ключей `Bundle`, и гарантированно опередить `CrashReportInitializer` нельзя.
Это же — готовый запрос вендору: публичный способ задать конфигурацию до
`init`.

## iOS синтезирует `issueKey`

В Dart-стектрейсе нет нативных адресов вызовов, а документация Tracer говорит,
что переданный массив `callStackSymbols` игнорируется, если не подключён
отладчик. В release-сборке группировать было бы попросту не по чему, и все
Dart-ошибки приложения схлопнулись бы в одну проблему.

Поэтому iOS-реализация выводит ключ из типа Dart-ошибки и её верхнего фрейма.
Явно переданный `issueKey` перекрывает это поведение.

## Зависания Dart-изолята не репортятся — пока

Это самый большой оставшийся пробел, и оставлен он намеренно, а не по
недосмотру.

Flutter-приложение может зависнуть, не породив ANR. Когда Dart-код блокирует
UI-изолят долгими синхронными вычислениями, кадры не рендерятся и для
пользователя приложение мертво — но происходит это в потоке `io.flutter.ui`, а
не в главном потоке Android, поэтому ни сторож ANR у Android, ни сторож Tracer
ничего подозрительного не видят. Это та же слепая зона, что и с Dart-ошибками,
только в другом обличье.

Tracer добавил механизм, способный донести такой отчёт:
`TracerCrashReport.reportThread(severity, thread)` (SDK 1.3.1) — он отправляет
состояние и стектрейс любого JVM-потока и предназначен для собственных
сторожей. Обнаружение зависания — это Dart-половина задачи, и она тоже
выполнима: сторожевой изолят, пингующий главный изолят через порт, заметит, что
ответы прекратились.

Две причины, почему это ещё не сделано:

* **Полезная нагрузка, скорее всего, будет пустоватой.** `io.flutter.ui` —
  нативный поток, исполняющий Dart VM. Его *Java*-стек покажет цикл сообщений, а
  не Dart-код, который на самом деле застрял, так что один `reportThread` может
  сказать немногим больше, чем «такой поток существует». Полезным артефактом был
  бы Dart-стек, снятый из сторожевого изолята, — а для него у SDK нет канала,
  кроме буфера логов. Стоит ли эта комбинация чего-нибудь, надо измерить, а не
  предполагать.
* **Это новый объём работ на непроверенном пакете.** Ничто в этом пакете пока не
  подтверждено на живом проекте Tracer. Добавлять фичу, ценность которой —
  гипотеза, до того как проверено ядро, значит делать это в неправильном
  порядке.

Добавить это позже — не ломающее изменение: `TracerPlatform` наследуется от
`PlatformInterface` именно затем, чтобы новые члены могли появляться совместимо.

## Вложения не предоставляются

В SDK 1.4.0 появился `UserSampleUpload.attachment()` — прикрепление файла
(скриншота, лога, дампа) к нефатальной ошибке через параметр `attachmentId`
метода `TracerCrashReport.report`. Вещь по-настоящему полезная, и здесь она не
обёрнута по двум причинам: вендор отмечает, что на сэмплы наложены куда более
жёсткие лимиты, чем на нефаталы, а в iOS SDK эквивалента нет вовсе — так что API
с первого дня был бы Android-only. Кроссплатформенный API для вложений стоит
спроектировать нормально, а не прикрутить сбоку.

## KGP применяется только под AGP 8, и не строчкой `apply plugin`

С AGP 9 Kotlin компилирует сам Android-плагин («Built-in Kotlin»), а применение
Kotlin Gradle Plugin из подпроекта-библиотеки больше не поддерживается — именно
на этом будущие версии Flutter будут валить сборку, о чём заранее предупреждает
`flutter build`. Официальный гайд для авторов плагинов предлагает выкинуть KGP
совсем и поднять минимум до Flutter 3.44: с этой версии flutter_tools сам
применяет KGP плагинам, которые его не объявляют. Здесь минимум остался
`>=3.22.0` — отрезать всех, кто на текущих стабильных релизах, ради
предупреждения не стоит, — поэтому KGP применяется по условию `agpMajor < 9`.

Применяется он через `pluginManager.apply('kotlin-android')`, а не строчкой
`apply plugin: 'kotlin-android'`. Flutter решает, мигрирован плагин или нет,
регуляркой по тексту `android/build.gradle`
(`FlutterPluginUtils.getSubprojectPluginState`), а не состоянием сборки —
буквальная форма продолжала бы числить пакет немигрированным из ветки, которая
на AGP 9 не выполняется. Обход детектора здесь совпадает с правдой: под AGP 9
пакет KGP не применяет.

Проверено на приложении с Flutter 3.44.9, AGP 9.1.1, Kotlin 2.3.20 и
`android.builtInKotlin=false`: пакет пропал из списка в предупреждении, сборка
проходит, классы плагина остаются с целью JVM 1.8. С `android.builtInKotlin=true`
не проверено — на Flutter 3.44.x этот путь не проходит ни у одного плагина:
там KGP применяется каждому подпроекту, который его не объявляет, мигрирован тот
или нет (flutter#187712, исправлено после 3.44.x).

Цель JVM выставляется тем DSL, который есть у текущего тулчейна:
`android.kotlinOptions` под Built-in Kotlin удалён, а верхнеуровневый
`kotlin.compilerOptions` отсутствует в KGP 1.x, который может оказаться на
класспасе у приложения на старом Flutter. Перечисление `JvmTarget` грузится
класслоадером самого расширения: в buildscript этого файла лежит своя копия KGP,
и под Built-in Kotlin это был бы другой класс с тем же именем.

## iOS собирается и Swift Package Manager, и CocoaPods

Flutter на каждой iOS-сборке пишет, что плагин с одним подспеком «does not
support Swift Package Manager» и что это «will become an error in a future
version of Flutter» — проверка живёт в `DarwinDependencyManagement`
(`darwin_dependency_management.dart`) и печатается независимо от того, включён
SPM в приложении или нет. Поэтому рядом с подспеком лежит `Package.swift`, а
исходники переехали в раскладку, которую ждёт SPM
(`ios/apptracer_flutter_ios/Sources/apptracer_flutter_ios`); подспек собирает
те же файлы, так что расхождению между двумя путями взяться неоткуда.

`OKTracer` объявлен там ровно так же, как в подспеке: зависимостью от
репозитория вендора по версии. Вендор публикует SDK бинарными таргетами в том
же `github.com/odnoklassniki/tracer-ios`, который служит его CocoaPods spec
repo, — значит принцип «ничего вендорского не редистрибутится и версия SDK не
фиксируется в чужой сборке» соблюдён и здесь. Имя продукта — `apptracer-flutter-ios`
через дефисы: SPM подставляет имя библиотеки в `CFBundleIdentifier`, где
подчёркивание недопустимо, и Flutter ищет продукт именно под этим именем.

Зависимости на `FlutterFramework` в манифесте нет — и это главное решение
здесь, потому что шаблон Flutter 3.44 её ставит, а `validatePluginSupportsSwiftPackageManager`
ругается на её отсутствие.

`FlutterFramework` — пакет, который Flutter генерирует для собственного
фреймворка. По исходникам flutter_tools его нет в 3.35 и 3.38, константа и
`flutterFrameworkSwiftPackageDirectory` появляются в 3.41, полностью он
генерируется в 3.44. Манифест, который на него ссылается, тем самым требует
3.41+, и приложение, включившее SPM раньше, упало бы на резолве
`../FlutterFramework`. Констрейнт `flutter:` один на оба пути, а CocoaPods
работает на всём `>=3.22.0`, так что выразить эту границу в pubspec нечем —
она осталась бы ловушкой в документации.

Проверено экспериментом, а не рассуждением: чистое приложение (`flutter create`
на 3.44.9, Podfile отсутствует, то есть search paths от CocoaPods исключены)
собирается обоими вариантами манифеста одинаково — плагин компилируется и
линкуется, в `Runner.debug.dylib` есть `AppTracerFlutterPlugin`, `DartLogProvider`
и `GeneratedPluginRegistrant`, рядом `TracerResources.framework` вендора.
Значит `import Flutter` резолвится через framework search paths, которые Flutter
передаёт сборке, и объявлять зависимость не обязательно.

Выбран вариант без неё: он резолвится на любой версии, где SPM вообще есть, и
не создаёт регресса для тех, кто включил SPM до 3.41. Цена — опора на поведение,
которое Flutter нигде не обещает: если он перестанет передавать search paths,
сборка сломается, и тогда зависимость придётся вернуть вместе с честным подъёмом
`flutter:`. Так же поставляются `url_launcher_ios` из самого `flutter/packages`
и `vkid_flutter_sdk`.

Продукт объявлен статическим: `OKTracer` — статический xcframework, и это то же
требование, которое на CocoaPods выражено через `use_frameworks! :linkage => :static`.

Само предупреждение при этом уходит: на 3.44.9 с включённым SPM Flutter вместо
него пишет «All plugins found for ios are Swift Packages». CocoaPods-путь
пересобран без изменений.

## Фаза выгрузки dSYM вынесена в отдельный скрипт

На CocoaPods фазу в `Runner.xcodeproj` добавляет подспек при `pod install`. На
SPM подспек не выполняется вообще, поэтому вставку фазы пришлось сделать
запускаемой отдельно — как у `firebase_crashlytics`, где это самостоятельный
`crashlytics_add_upload_symbols`, вызываемый подспеком.

Сам текст фазы теперь лежит файлом `ios/tracer_dsym_upload_phase.sh`, а не
heredoc-ом внутри Ruby: это единственный источник правды сразу для трёх
потребителей — подспека, ручной вставки в Xcode и README. Поверх скрипта есть
команда `dart run apptracer_flutter:install_ios_dsym_phase`, которая находит
пакет через package config и запускает его, чтобы никто не выуживал путь из
pub-cache руками. Ruby с gem `xcodeproj` она требует — той же парой пользуется
CocoaPods, — и говорит об этом, если их нет.

## Версия — ниже `1.0.0`

Доставка событий не подтверждена на живом проекте Tracer, потому что для этого
нужны учётные данные, которых у этого репозитория нет. Публиковать `1.0.0`
значило бы заявить стабильность, которую никто не проверял. В
[status.md](status.md) перечислено ровно то, что доказано; версия станет
`1.0.0`, когда колонка непроверенного опустеет.
