# Задача: управление нативным сбором Tracer после согласия

**Создана:** 1 октября 2026.
**Статус:** реализация и проверка сбора/отзыва завершены 3 октября 2026. Android SDK 1.4.0 проверен в release/R8 на API 35, OKTracer 1.5.2 — на iPhone; Web — в Chrome. Контрольные отчёты подтверждены в Tracer. Ограничения символизации записаны в журнале. Шесть пакетов опубликованы на pub.dev как стабильный `0.2.0`; миграция приложений не выполнялась.
**Приоритет:** высокий; требуется для необязательной диагностики в приложении «Сад», п. 100/19.
**Основной пакет:** `apptracer_flutter_android`.
**Связанные пакеты:** `apptracer_flutter`, `apptracer_flutter_platform_interface`, `apptracer_flutter_ios`.

## Проблема

На Android нативный Tracer запускается через `ContentProvider` до выполнения Flutter-кода.
`TracerOptions.isCollectionEnabled=false` останавливает запуск Dart-клиента, но само по себе
не запрещает автоматический нативный сбор и отправку. Текущий Android-метод `initialize`
проверяет наличие SDK, ресурсов Gradle-плагина и `Tracer.isDisabled`, предполагая, что SDK
уже инициализирован.

Для запуска только после согласия приложение сейчас вынуждено самостоятельно удалять providers
из manifest, запускать нативный SDK, останавливать его и очищать ожидающие отправки отчёты
через собственный `MethodChannel`. Эти операции должны принадлежать платформенной реализации
Tracer и быть доступны через общий Dart API пакета.

На iOS другая исходная ситуация: `initialize` создаёт сервис и вызывает `created.start()`,
а `stopCollection` вызывает `service.stop()` и очищает `DartLogProvider`. Отложенный старт уже
возможен, но очистка сохранённых нативных отчётов, прекращение фоновых отправок и безопасность
повторного `initialize` текущим кодом не подтверждены.

## Цель и границы

Приложение управляет запуском, остановкой и очисткой диагностики через API `apptracer_flutter`,
без собственного нативного кода, отдельного канала и знания внутренних каталогов SDK.

Плагин не проверяет серверное согласие, его редакцию, локаль или принадлежность аккаунту.
Это ответственность приложения. Приложение разрешает запуск после своей проверки и вызывает
остановку с очисткой при отзыве согласия, logout или смене пользователя. Плагин обеспечивает
технический жизненный цикл транспорта, а не хранение юридических доказательств.

Работа охватывает Android и соответствующий контракт iOS. Для остальных реализаций сохранить
совместимость федеративного интерфейса и явно описать поддержку новых операций.

## Что сделать

### 1. Общий Dart API и состояние транспорта

- [x] Предусмотреть режим отложенной нативной инициализации и явный запуск после решения приложения.
      Разделить одноразовый bootstrap с `appRunner` и последующее управление сбором: переключение
      диагностики не должно повторно запускать приложение или создавать лишние охраняемые зоны.
- [x] Предоставить остановку с очисткой ожидающих отправки отчётов и диагностических буферов.
      Операция должна работать и до успешного старта Dart-клиента: сейчас `TracerClient.stop()`
      вызывает платформенную остановку только при `_started=true`.
- [x] Возвращать фактическое состояние и результат операций. Различать работающий сбор, выключенный
      сбор, необходимость перезапуска, отсутствие реализации и ошибку запуска/необходимой очистки.
      Окончательные имена типов и методов определить при реализации.
- [x] Сразу запрещать новые Dart-события при остановке, до асинхронного завершения native-вызова.
      Проверить ошибки, breadcrumbs, логи, custom keys и пользовательские идентификаторы:
      выключенный сбор не должен накапливать их для последующей отправки.
- [x] Сделать повторные вызовы и гонку запуска/остановки безопасными. Поздний ответ запуска
      не должен разрешать сбор после уже полученной команды остановки.
- [x] Сохранить гарантию `appRunner`: ровно один вызов при любом исходе bootstrap, включая
      выключенный сбор, отсутствие SDK и ошибку инициализации.

### 2. Android: отложенный нативный запуск

- [x] Добавить документированную настройку режима на уровне manifest или сборки, которая действует
      до Flutter и исключает автоматический старт SDK через providers. Одного runtime-параметра
      Dart недостаточно. Проверить vendor `InitializationProvider` и `TracerAutoConfigProvider`.
- [x] В отложенном режиме запускать нативный SDK внутри Android-плагина после явной команды
      из Dart. Сохранить необходимые конфигурации и metadata инициализаторов, Gradle-ресурсы,
      проверку наличия SDK и обработку отсутствующего токена.
- [x] Согласовать порядок очистки, установки конфигурации и запуска так, чтобы необходимая
      очистка завершалась до начала работы отправителей. При её ошибке оставлять сбор выключенным.
- [x] Останавливать нативный сбор, фоновые отправки и повторные попытки в пределах возможностей SDK.
      Проверить фактическое поведение `Tracer.disable()`, а не считать переключение флага
      доказательством отмены уже запущенных работ.
- [x] Не отправлять отчёты, которые приложение приказало удалить после отзыва/смены пользователя.
      Определить безопасную политику для отчётов от предыдущего запуска и описать момент очистки.
      Предпочесть поддерживаемый API SDK; если нужны внутренние API или каталоги, зафиксировать
      проверенные версии, границы очистки и тест обновления SDK.
- [x] Учесть необратимость отключения в одном процессе. Если новый запуск невозможен, возвращать
      необходимость перезапуска и не выдавать `isEnabled=true`.
- [x] Проверить process-scoped состояние при повторном подключении плагина, нескольких engines
      и пересоздании Activity. Новый экземпляр плагина не должен обходить остановку старого.
- [x] Зафиксировать стратегию совместимости существующего автоматического режима. Не менять
      поведение опубликованных интеграций молча; при ломающем изменении дать план миграции.

### 3. iOS: проверить и обеспечить тот же контракт

Отключение Android ContentProvider на iOS не требуется. Нужна проверка следующих гарантий
и реализация недостающих частей:

- [x] До явного разрешения приложения не создавать и не запускать сервис OKTracer.
- [x] Проверить запрет новых отчётов и повторных отправок после остановки.
      На iPhone пройдены offline/in-flight и fatal-after-revoke проверки: хранилища
      очищаются и блокируются. Уже начатый запрос может завершиться; нативный
      crash handler остаётся установленным, но не сохраняет новый отчёт.
- [x] Проверить хранение crash reports и других нативных отчётов. Очистка `DartLogProvider`
      не является доказательством очистки SDK-хранилища. Реализовать удаление отчётов,
      которые не должны отправляться после отзыва или смены пользователя.
- [x] Не создавать второй работающий сервис при повторном `initialize`. Три дополнительных
      Flutter engine на iPhone подтвердили общее терминальное состояние. Остановленный
      сервис без delegate удерживается до завершения процесса из-за гонки SDK; повторно
      он не используется.
- [x] Проверить допустимость повторного запуска после остановки и возвращать реальный результат.
      Не переносить ограничение Android на iOS без проверки SDK.
- [x] Зафиксировать границы API OKTracer: адаптер привязан к 1.5.2 и проверенным
      путям хранения; при ошибке очистки сбор остаётся выключенным. Это подтверждено
      инъекцией ошибки на iPhone; ограничение crash handler и удержания объекта описано.

## Проверки и критерии приёмки

- [x] Чистая установка и холодный старт в отложенном режиме: до разрешения приложения нет
      нативного сбора, диагностических файлов и сетевых запросов к Tracer.
- [x] Выключенный Dart bootstrap вызывает `appRunner` один раз и не разрешает нативный сбор.
- [x] Явный запуск после разрешения включает транспорт; тестовые Dart-ошибка и нативный сбой
      доставляются и правильно отображаются в Tracer.
      Подтверждены типы событий, JVM/ANR-имена, iOS-символы и восстановленный Web-кадр.
      Полная расшифровка Android minidump не заявляется: ограничения ниже.
- [x] Остановка запрещает новые события и буферизацию диагностических данных. Проверены
      фоновые отправки и повторные попытки, в том числе после восстановления сети.
- [x] Сценарий offline → событие → остановка с очисткой → восстановление сети не отправляет
      удалённый отчёт. То же проверено после завершения и нового запуска процесса.
- [x] Смена пользователя через остановку с очисткой не переносит старые отчёты, идентификаторы,
      custom keys и breadcrumbs в следующий период сбора.
- [x] Повторные запуск/остановка, остановка во время запуска и пересоздание engine не создают
      дублирующих сервисов и не обходят запрет сбора.
- [x] Ошибки очистки, отсутствие SDK, отсутствие токена и ошибки запуска не роняют приложение
      и не дают ложного состояния «сбор включён».
- [x] Проверен повторный запуск после остановки: работающий транспорт либо явная необходимость
      нового процесса. Состояние подтверждено нативной реализацией.
- [x] Есть Dart unit-тесты и платформенные тесты жизненного цикла. На устройстве/эмуляторе
      проверены нативные файлы и сетевой трафик, включая фатальный сбой с последующим запуском.
- [x] Проверена Android release-сборка с R8 и нативными модулями crash/ANR. SDK API, metadata
      и вызовы старта не теряются при оптимизации.
- [x] Для iOS отдельно проверены нативные отчёты, остановка, очистка и повторный запуск.
      Подтверждение Android не считается подтверждением iOS.

Отчёты, уже переданные серверу до остановки, эта операция не удаляет. Удаление серверных данных —
отдельная процедура приложения и обработчика. В документации также отделить уже начатые сетевые
запросы от новых отправок и подтвердить реальные возможности их отмены.

## Связь с приложением «Сад»

После выпуска пакетов приложение должно заменить свой `farming/crash_collection` и
`CrashCollectionChannel.java` вызовами общего API. Решение о согласии и офлайн-очередь отзыва
остаются в приложении. Его release-флаги не включать автоматически при обновлении зависимости.

Завершение этой задачи подтверждает возможности транспорта. Приёмка п. 100/19 приложения
дополнительно проверяет серверное согласие, отзыв, применимость документов и реальное событие.

не выдаёт ошибку прогрева сети, но SDK возвращает `error / native_start_failed`
из `ios-native`. Это отдельный блокер; до проверки отзыва после активного
старта тест не дошёл.
