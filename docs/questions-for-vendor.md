**Модули с не-исполняемым первым сегментом получают нулевой build id и сдвинутую
базу.**

Спасибо за ответ про `additionalLibrariesPath` — залил символы Dart ровно так,
как вы описали (без `forceUpload`, подставной `libapp.so` в папке), плагин
написал `Uploading libapp.so:F99DCFDB63383B227E98F3EEAD446A130`. Дальше уронил
процесс так, чтобы сбойная инструкция была именно внутри кода Dart: запись по
невалидному адресу через `dart:ffi`, то есть обычная инструкция внутри
`_kDartIsolateSnapshotInstructions`.

Отчёт пришёл такой:

```
No symbols found for these libs (4): base.vdex (0…0), libflutter.so (0…0),
                                     base.odex (103A87…), libapp.so (0…0)
Thread 0 (crashed)
0  libapp.so + 0xa5234
```

Системный анвайндер того же краша на том же устройстве пишет:

```
#00 pc 0000000000155234  …/lib/arm64/libapp.so (offset 0xb0000)
                         (BuildId: dbcf9df93863223b7e98f3eead446a13)
```

То есть у вас `libapp.so` с нулевым id и смещением `0xa5234`, у системы — та же
библиотека с настоящим build id и смещением `0x155234`. Разница ровно `0xb0000`.

`0xb0000` — это file offset сегмента с кодом. Program headers:

| библиотека | код по file offset | `.note.gnu.build-id` |
|---|---|---|
| `libapp.so` | `0xb0000` | offset `0x1c8` — в другом маппинге |
| `libflutter.so` | `0x454080` | offset `0x270` — в другом маппинге |
| `libtracernative.so` | `0x0` | offset `0x238` — в том же маппинге, что и код |

Похоже, репортёр опознаёт модуль по маппингу, в который попал адрес, и читает
ELF-идентичность с начала этого маппинга. `libapp.so` мапится по одному
маппингу на `PT_LOAD`, код лежит с `0xb0000`, и маппинг с местом падения
начинается с середины файла — там нет ни ELF-заголовка, ни
`.note.gnu.build-id`. Отсюда и нулевой id, и база, укороченная ровно на
смещение сегмента с кодом. Ваша `libtracernative.so`, у которой код с нулевого
смещения, этим не задета — в отчёте нулевой id получили ровно `libapp.so` и
`libflutter.so`.

Проверил, что дело именно в этом, а не в правах сегмента: пропатчил в
поставляемой `libapp.so` `p_flags` первого `PT_LOAD` с `r--` на `r-x`, чтобы
самый нижний исполняемый маппинг файла начинался с нулевого смещения и содержал
ELF-заголовок, пересобрал и переподписал APK. Приложение работает штатно, отчёт
пришёл побайтно тот же — нули и `+ 0xa5234`. То есть других маппингов того же
файла репортёр не смотрит.

Практические следствия два, и второе шире моего сценария:

1. Символы, залитые через `additionalLibrariesPath`, применить невозможно: вы
   ищете `libapp.so` с id `F99DCFDB…30`, а в минидампе `libapp.so` с id `0…0`.
   И даже при совпадении id имена были бы не те: все адреса на `0xb0000` меньше.
2. **Кадры внутри `libflutter.so` не читаются ни у кого из пользователей
   Flutter** — по той же причине, независимо от Dart и от загрузки символов.

Вопросы: это известное поведение? Планируется ли починка — в upstream breakpad
это решается вычитанием `mapping.offset` перед чтением ELF, чтобы база модуля
указывала на начало файла, а не на начало маппинга. И есть ли всё-таки
обходной путь на стороне приложения: `useLegacyPackaging = true` чинит только
имя модуля (без него было `base.apk + 0xa5234`), патч сегмента, как выше, не
меняет ничего, и больше идей у меня нет.

Проверял на Android 10 (CLT-L29), `tracer-crash-report-native` 1.4.0,
release-сборка с `--obfuscate --split-debug-info`.

## Отвечено

### 1. Символы Dart (`--split-debug-info`) — отвечено 27.08.2026

Вопрос был задан так:

> **1. Символы Dart (`--split-debug-info`).**
>
> Flutter при сборке с `--obfuscate --split-debug-info` кладёт имена Dart-функций
> в отдельный ELF-файл `app.android-arm64.symbols` с тем же GNU build-id, что и у
> `libapp.so` в APK.
>
> Проверил локально вашей же утилитой `dump_syms` из `tracer-plugin-1.4.0.jar`:
>
> ```
> dump_syms app.android-arm64.symbols  -> MODULE Linux arm64 F99D...D70, 7545 FUNC с именами Dart
> dump_syms libapp.so (stripped)       -> MODULE Linux arm64 F99D...D70, 0 FUNC
> ```
>
> То есть модуль тот же, а символы есть только в первом файле. Отсюда вопросы:
>
> По `ParsedSymbolFile.Quality` первый файл — `FULL`, второй — `CFI_ONLY`
> («No usable symbols found...»). В самом плагине есть сообщение: «If you're using
> additionalLibrariesPath to provide symbol overrides for libraries packaged into
> your application...» — то есть сценарий «положить лучшие символы для библиотеки,
> упакованной в приложение», выглядит поддерживаемым. Отсюда вопросы:
>
> - а) Я это сделал: положил файл в `additionalLibrariesPath` под именем
>   `libapp.so` (чтобы совпали и имя модуля, и build-id) и включил
>   `forceUploadNativeSymbols = true`. Загрузка проходит — плагин пишет
>   `Uploading libapp.so:<build-id>` для всех трёх архитектур и сборка успешна;
>   без принудительного флага он их пропускал, отвечая `Uploading them anyway due
>   to forced upload` только с ним. Вопрос в другом: **применяются ли** эти
>   символы к кадрам внутри `libapp.so` в нативных крашах и минидампах? Со
>   стороны клиента этого не видно.
> - б) В `ParsedSymbolFile` есть `originalLibHash` — хэш файла, из которого
>   сгенерированы символы. У нас это файл символов Dart, а не настоящий
>   `libapp.so`, поэтому хэш отличается. Сопоставление на бэкенде идёт по
>   build-id или по этому хэшу? Если по хэшу — сценарий не сработает, и хотелось бы
>   знать это заранее, а не по молчанию.
> - в) Есть ли отдельный, «правильный» канал для debug-файлов Dart — например,
>   Sentry-совместимый `debug-files upload` (chunk-upload API), если проект заведён
>   с Sentry DSN?
>
> Понимаю, что даже при положительном ответе это поможет только нативным крашам:
> у ручного `TracerCrashReport.report` Dart-стектрейс — это текст, привязывать
> символы не к чему.
>
> Заодно мелочь: в том самом сообщении плагина опция названа
> `dontWarnAboutLibraryConflicts`, а в `TracerConfig` и в документации она
> `dontWarnOnLibraryConflicts`. Похоже на опечатку в тексте предупреждения.

**Ответ вендора, дословно:**

> а) да, можно положить libapp.so в папку, скормить ее в additionalLibrariesPath
> и оно возьмёт символы с бонусной папочной либы
>
> forceUpload лучше не включать, он отключает только проверку на наличие такихто
> символов на бекенде (оно по дефолту не загружает если уже есть либа с таким же
> именем и build id, ибо натив обычно нечасто пересобирают)
>
> чтоб не ругалось на конфликты (между приложеньковым libapp.so и папочным
> libapp.so) был отдельный флаг про dontWarnAboutLibraryConflicts и он куда-то
> пропал
>
> вообще все это делалось для сложных запросов вида "мы очень не хотим чтоб агп
> в принципе никогда не видел unstripped-либы, поэтому мы хотим способ перекрыть
> stripped-либы в билде unstripped-либами снаружи" - потому там варнинги на
> случай конфликтов только если ожни символы не-очевидно-лучше других
>
> но перекрывать/добавлять через такое можно, да
>
> б) это "хеш" из файла, то бишь из заголовка (MODULE ...)
>
> там по формату брейкпада типа-uuid+age ибо они его по виндовым пдб писали, но
> по факту там обрезанный-растянутый .note.gnu.build-id, который обычно ~sha1 -
> потому оно и "хеш"
>
> сопоставление как у minidump-stackwalk - по этим типаууидам от
> .note.gnu.build-id, сценарий должен сработать

**Что это меняет.**

* Сценарий подтверждён как штатный, а не как трюк: подмена stripped-либы
  внешним файлом — то, ради чего `additionalLibrariesPath` и делался.
* Сопоставление идёт по build-id (по типа-uuid из `.note.gnu.build-id`), не по
  содержимому файла. Подпункт «б» закрыт. Заодно снято и наше опасение про
  `ParsedSymbolFile.originalLibHash`: в байткоде это SHA-1 самого файла, он
  считается только внутри `handleSameSymbols`, чтобы решить, одна и та же это
  библиотека или разные, и в загрузку не попадает вообще.
* `forceUploadNativeSymbols` убран из `example/android/app/tracer.gradle`.
  Здесь ответ вендора точен по смыслу, но неполон по механике: флаг гейтит две
  вещи, и проверка `nativesymbol/exists` — вторая. Первая — выкидывание из
  списка загрузки всего, что разобралось хуже `FULL`. Наш подставной файл —
  `FULL`, поэтому его не трогает ни то, ни другое, и форсировать нечего.
  Прежняя запись в `symbolication.md` была неверной и исправлена: строка
  `Uploading them anyway due to forced upload` из живого прогона 26.08.2026
  относилась к первому фильтру и к другим библиотекам, а не к exists-проверке.
* Про конфликты предупреждения и не будет: `handleSameSymbols` для `FULL`
  поверх не-`FULL` пишет в debug «assuming symbol upgrade» и выходит, не
  выставляя `libConflictFound`. Это ровно то, что вендор описывает словами
  «варнинги … только если ожни символы не-очевидно-лучше других».
* Флаг никуда не пропадал: в 1.4.0 он есть в `TracerConfig` и
  `MergedTracerConfig` под именем `dontWarnOnLibraryConflicts`. Расходится
  только текст самого предупреждения, где он назван
  `dontWarnAboutLibraryConflicts` — это и есть та опечатка, про которую мы
  писали. Нам он всё равно не нужен.

**Что осталось.** Подпункт «в» (отдельный, Sentry-совместимый канал для
debug-файлов Dart) ответа не получил — спросить повторно, если появится
потребность в автоматической загрузке.

**И главное: «сценарий должен сработать» не сработал.** Проверка №16 проведена
27.08.2026 и дала отрицательный результат — но не по вине бэкенда и не по вине
сопоставления, которое вендор описал верно. Нативный репортёр SDK записывает
`libapp.so` с нулевым build id и с базой, сдвинутой на смещение исполняемого
сегмента, так что сопоставлять просто не с чем. Разбор — в
[symbolication.md](symbolication.md), находка 2; дефект оформлен вторым
сообщением в разделе «Send now».

## Ask only if a check fails

### 3. Группировка NON_FATAL на iOS — если провалится проверка №10

По документации («Символизация и группировка сбоев») для нефатальных ошибок
группировка идёт именно по `issueKey`, если он задан. Обёртка на это и
рассчитывает: генерирует `dart/<Тип>/<метод>` — без файла и строки, чтобы ключ
не менялся при правках кода.

Спрашивать здесь нечего, пока проверка №10 не провалится. Если провалится —
значит, `issueKey` работает не так, как описано, и вопрос будет звучать так:
почему события с разными `issueKey` попали в одну группу (или наоборот)?
Приложить два `crashId` и оба `issueKey`.

### 4. Снят 26.08.2026 — DSN не нужен

Вопрос звучал «как получить DSN для web». Ответ выяснился сам: DSN нет ни у
одного проекта, и он не нужен. Распакованный с npm `@apptracer/sdk` 2.6.9 шлёт
события в собственный приём Tracer — `POST /api/crash/uploadBatch`, авторизуясь
`appToken`, — и пакет теперь делает то же самое. Формат снят перехватом живого
запроса и описан в [web-protocol.md](web-protocol.md); он принят живым сервером.

Оба остававшихся вопроса по этому поводу закрыты 27.08.2026 — и спрашивать
вендора не понадобилось, ответы нашлись в его же бандле (`lib/main/index.mjs`,
классы `LogsData` и `StackTraceUploader`) и одной живой пробой:

* `trackSession` для приёма событий **не нужен** — это отдельный модуль
  `SessionUploader`, он кормит метрику crash-free и на `/api/crash/uploadBatch`
  не влияет.
* Breadcrumbs — `logsFile`, base64 от строк `#<индекс> <epoch millis> | <текст>`
  с капом 64 000 байт. Реализовано и проверено живьём.

Разбор — в [web-protocol.md](web-protocol.md).
