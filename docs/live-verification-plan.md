# План проверки на живом проекте

Пошаговый чек-лист от «есть аккаунт в Tracer» до «можно публиковать».

Всё, что здесь написано, проверено локально: команды запускались, сниппеты
компилировались. Не проверено ровно одно — что события реально доезжают до
Tracer, потому что для этого нужны ваши токены. Именно это мы и закрываем.

**Ориентир по времени:** 3–4 часа активной работы, растянутых на несколько
дней из-за ожидания ответов вендора.

## Этап 0. Доступы



### 0.1 Проекты в Tracer

**Важно:** Tracer заводит проект под конкретную платформу, и `appToken` у
каждого свой. Для полной проверки нужно **три отдельных проекта**:

- [ ] Android-проект → `appToken`, `pluginToken`
- [ ] iOS-проект → `appToken`, `pluginToken`
- [ ] JS-проект → `appToken`, `pluginToken`

Токены лежат в разделе **Настройки** проекта. Создавать проекты может владелец
или администратор организации.

### 0.2 Sentry DSN для web

Web в этом пакете ходит по протоколу Sentry, а не через JS SDK — почему именно
так, написано в [design-decisions.md](design-decisions.md). DSN выдаётся в
разделе **Настройки → API** проекта. Если его там нет, проект нужно завести
через VK Cloud — Tracer описывает это в разделе «Другие платформы».

- [ ] `TRACER_DSN` получен — **не удалось 26.08.2026.** В созданном JS-проекте
  раздела с DSN нет: в «Настройки → Проект → API» только `appToken` и
  `pluginToken`, в документации вендора DSN не описан. Ушло вопросом №4 в
  [questions-for-vendor.md](questions-for-vendor.md); до ответа проверки 13 и 14
  не начать.

## Этап 3. Android



### 3.1 Gradle

`android/settings.gradle.kts` — плагин Tracer лежит на **Maven Central**, а не в
Gradle Plugin Portal:

```kotlin
pluginManagement {
    repositories {
        google()
        mavenCentral()
        gradlePluginPortal()
    }
}

plugins {
    id("ru.ok.tracer") version "1.4.0" apply false
}
```

`android/app/build.gradle.kts`:

```kotlin
plugins {
    id("com.android.application")
    id("kotlin-android")
    id("dev.flutter.flutter-gradle-plugin")
    id("ru.ok.tracer")
}

android {
    buildFeatures {
        resValues = true
    }
}

tracer {
    create("defaultConfig") {
        // Не System.getenv: скрипт исполняется в демоне Gradle, а тот
        // наследует окружение шелла, который его запустил. Демон живёт между
        // сборками, поэтому экспортированные позже токены останутся невидимы.
        appToken = providers.environmentVariable("TRACER_ANDROID_APP_TOKEN").orNull
        pluginToken = providers.environmentVariable("TRACER_ANDROID_PLUGIN_TOKEN").orNull
        uploadMapping = true
        uploadNativeSymbols = true
        uploadRetryCount = 2
    }
}

dependencies {
    implementation(platform("ru.ok.tracer:tracer-platform:1.4.0"))
    implementation("ru.ok.tracer:tracer-crash-report")
    implementation("ru.ok.tracer:tracer-crash-report-native")
}
```

- [ ] собирается: `flutter build apk --debug`



### 3.2 Включить загрузку из debug-сборки

**В примере из репозитория это уже сделано** — см.
`example/android/app/src/tracer/kotlin/.../TracerHostApplication.kt`. Класс
лежит в отдельном source set, который подключается только при
`-Ptracer.enabled=true`, поэтому чекаут без токенов продолжает собираться.
Ниже — то же самое для вашего приложения.

**Это главная ловушка этапа.** По умолчанию Android SDK Tracer **не отправляет
ничего из debug-сборки**, и первые полчаса легко потратить на поиск событий,
которых физически нет.

Два выхода. Первый — собирать release. Второй, удобнее для отладки, — свой
`Application`. Сниппет ниже скомпилирован и собран, не «по документации»:

`android/app/src/main/kotlin/<ваш/пакет>/TracerHostApplication.kt`:

```kotlin
package ваш.пакет

import android.app.Application
import ru.ok.tracer.CoreTracerConfiguration
import ru.ok.tracer.HasTracerConfiguration
import ru.ok.tracer.TracerConfiguration
import ru.ok.tracer.crash.report.CrashFreeConfiguration
import ru.ok.tracer.crash.report.CrashReportConfiguration

class TracerHostApplication : Application(), HasTracerConfiguration {
    override val tracerConfiguration: List<TracerConfiguration>
        get() = listOf(
            CoreTracerConfiguration.build {
                // Без этого из debug-сборки не уйдёт ни одно событие.
                setDebugUpload(true)
            },
            CrashReportConfiguration.build {
                setSendAnr(true)
                setExperimentalNonFatalRateLimitEnabled(true)
            },
            CrashFreeConfiguration.build {
                setEnabled(true)
            },
        )
}
```

В `android/app/src/main/AndroidManifest.xml` — **заменить**, а не добавить:
у Flutter там уже стоит `android:name="${applicationName}"`, и второй
`android:name` ломает сборку с ошибкой слияния манифестов.

```xml
<application
    android:name=".TracerHostApplication"
    ...>
```

- [ ] собирается
- [ ] в логах при старте виден Tracer



### 3.3 Запуск

Для примера из репозитория — целью Makefile, она уже знает про флаги:

```sh
make example-android                      # из корня репозитория
make -C packages/apptracer_flutter/example android   # то же самое
```

Если пример открыт отдельным проектом, в его папке лежат свой `Makefile`
(`make android`) и `.vscode/launch.json` с теми же запусками.

Что она делает и почему именно так:

```sh
source ~/.tracer-env
cd packages/apptracer_flutter/example
flutter run --release -Ptracer.enabled=true
```

**`-Ptracer.enabled=true` обязателен.** В примере плагин Tracer опционален,
чтобы чекаут без токенов собирался. Без флага не подключаются ни зависимости
`ru.ok.tracer`, ни ресурс `tracer_app_token` — плагин это увидит, выключится, и
в карточке состояния будет «сбор включён: false».

**`--dart-define=TRACER_APP_TOKEN` на Android не нужен** — токен приходит из
Gradle-плагина, который на этапе сборки пишет его в строковый ресурс. Переданный
из Dart токен игнорируется, о чём в лог уходит предупреждение.

В вашем приложении (вариант B) плагин применяется безусловно, флаг не нужен:

```sh
source ~/.tracer-env
flutter run --release
```

Наши собственные логи:

```sh
adb logcat -s apptracer_flutter
```

`TracerOptions(debug: true)` включает диагностику на стороне Dart — в консоли
Flutter появится строка вида `apptracer_flutter: started with backend "android-native"`. Если её нет, дальше идти бессмысленно.

Если Tracer молчит, поднимите его собственное логирование:

```kotlin
class TracerHostApplication : Application(), HasTracerConfiguration, HasTracerLogger {
    override val tracerLoggerDelegate: TracerLoggerDelegate
        get() = DefaultTracerLoggerDelegate(minLogPriority = Log.VERBOSE)
    // ...
}
```



### 3.4 Проверки

**Нажимать всё руками не обязательно.** Автопрогон:

```sh
make example-live-check     # из корня; из папки примера — make live-check
```

Он запускает настоящее приложение на подключённом устройстве, нажимает кнопки в
правильном порядке, проверяет то, что видно со стороны Dart (сбор включён,
ошибки дошли до обработчиков, `stopCollection` выключил сбор), и печатает в
конце список того, что осталось сверить глазами.

Три вещи автопрогон не делает, и это не лень, а ограничения:

* **Не проверяет, что событие доехало до Tracer и как оно выглядит.** У Tracer
  нет публичного API на чтение событий — только на загрузку символов и
  сорсмап. Заголовок, группировку и вкладки «Логи» и «Данные» смотрите руками.
* **Не нажимает «Бросить асинхронно» и «Бросить из future без await».** Таймер
  наследует зону, активную в момент создания, а `tester.tap` вызывается из зоны
  теста, не из защищённой зоны приложения. Ошибка уходит тестовому фреймворку и
  до нашего обработчика не доходит вовсе. В обычном запуске приложения всё
  работает.
* **Не делает проверки 7 и 8** (нативный краш и ANR): первая убивает процесс,
  вторая вешает главный поток, драйвер в обоих случаях теряет соединение.

Дальше — полный ручной список, он же служит справочником при разборе
автопрогона.

События приходят не мгновенно — подождите пару минут и обновите список.


| #   | Что нажать                                          | Где смотреть      | Признак успеха                                                                     |
| --- | --------------------------------------------------- | ----------------- | ---------------------------------------------------------------------------------- |
| 1   | «Отправить пойманную ошибку»                             | Сбои → список     | событие появилось                                                                  |
| 2   | там же                                              | заголовок события | читается `DartError: FormatException: could not parse the response` — класс исключения в Tracer всегда `DartError`, тип Dart вынесен в начало сообщения |
| 3   | там же                                              | стектрейс         | видны кадры вида `_HomePageState.build(package:.../main.dart:78)`, а не только JNI |
| 4   | «Бросить синхронно», затем «Бросить асинхронно» | список            | **две разные группы**, не одна                                                     |
| 5   | «Добавить breadcrumb», затем любую ошибку              | событие → Логи    | строка `... [info] ui | user tapped...`                                            |
| 6   | «Задать кастомный ключ», затем ошибку                    | событие → Данные  | `checkout_step = 3` и `dart.exception_type`                                        |


Проверка 3 — самая важная. Если стектрейс состоит из JNI-кадров, значит
`DartError.toStackTrace` не отработал, и группировка на Android бесполезна.

**Находка (26.08.2026): проверка 4 провалена на Android.** Tracer сгруппировал
в одну проблему три разных события:

```
StateError: Bad state: synchronous Dart failure    main.dart:148
StateError: Bad state: synchronous Dart failure    main.dart:135
TimeoutException: unawaited future failure         main.dart:150
```

Разные типы исключений, разные сообщения, разные строки; у первого ещё и стек
другой — он пришёл из автопрогона и несёт кадры `flutter_test`. Совпадает
единственное: верхний кадр читается как `_HomePageState.build.<anonymous
closure>`. Вывод: ключ группировки на Android — имя класса и метода верхнего
кадра, и только оно. Ни тип исключения, ни сообщение в него не входят.

Для Flutter-приложения это плохо: почти все обработчики — анонимные замыкания
внутри одного `build`, так что ошибки разной природы будут схлопываться в одну
кучу. Ровно из-за этого на iOS мы синтезируем `issueKey` из типа ошибки и
верхнего кадра; на Android положились на группировку по внедрённому стеку — и
зря.

Побочно это же наблюдение **закрывает проверку 20**: события со строк 135 и 148
попали в одну группу, то есть сдвиг кода группу не разрывает.

**Исправлено 26.08.2026.** Когда вызывающий код не задал `issueKey`, он теперь
синтезируется из типа ошибки и внутреннего именованного кадра —
`SyntheticIssueKey` в `apptracer_flutter_platform_interface`. Правило то же,
что уже было на iOS, вынесено в Dart, чтобы обе платформы делили одну
реализацию; бэкенды, которые группируют сами по достаточным данным (транспорт
Sentry), ключа не получают. Ни файл, ни строка в ключ не входят, так что
проверка 20 не ломается.

Перепройдено в тот же день: `StateError` и `TimeoutException`, брошенные из
одного и того же места, легли в разные группы —
`[d/ild.<anonymous closure>#5ef264]` и `[d/ild.<anonymous closure>#4ae405]`.
Группы, созданные до исправления, остались слипшимися: переписать историю в
Tracer нечем.

**Находка (26.08.2026).** Дословный стектрейс, который пишет
`attachRawStackTraceAsLog`, — это одна многострочная запись лога. Табличное
представление вкладки «Логи» в консоли Tracer её не рисует и показывает вместо
неё «ошибка форматирования данных»; текстовое представление той же вкладки
отдаёт содержимое целиком и без потерь. То есть данные доезжают, ломается
только табличный рендер. Однострочные breadcrumbs отображаются нормально.

Причина — в тексте самой ошибки:

```
Ошибка форматирования текста. Вы можете посмотреть исходный текст во вкладке "Текст":
Match line error, expected format: #0 timestamp | text
```

Консоль ищет **следующий по порядку** номер записи и пытается разобрать
найденное как `#N timestamp | text`. Трейс, лежащий в записи `#2`, через
несколько строк подсовывает ей собственный кадр `#3`. Обфусцированный трейс
спасается случайно: его кадры пронумерованы `#00`, `#01`, и парсер, ищущий
`#2`, на них не натыкается.

По дороге были две ложные версии, обе отброшены измерением: размер записи
(2651 байт рисуется, 3580 нет — совпадение) и отступ (пробел в начале строки
ничего не изменил, парсер нашёл `#3` и так).

**Исправлено 26.08.2026.** `defuseFrameNumbers` переписывает номера кадров в
`[0]`, `[1]` — но только у читаемых трейсов. Обфусцированный уходит дословно:
его принимает `flutter symbolize`, и консоль его и так рисует.

Проверки 7 и 8 (нативный краш и ANR) — это работа нативного SDK, не наша, но их
стоит подтвердить, чтобы знать, что связка вообще жива. В примере под них есть
секция «Нативные сбои», она видна только на Android. Делайте их **последними**:
обе завершают сеанс.

- [ ] **нативный краш** — кнопка «Уронить процесс нативно». Шлёт SIGSEGV
  собственному процессу; обработчик сигналов из `tracer-crash-report-native`
  ловит его так же, как настоящий segfault. Процесс умирает — запустите
  приложение заново, событие уедет при следующем старте.
- [ ] **ANR** — кнопка «Заблокировать главный поток (ANR)». **Нужен Android 11
  или новее**: `AnrReporter.collect` в `tracer-crash-report` 1.4.0 начинается с
  `if (SDK_INT < 30) return emptyList()` и читает
  `getHistoricalProcessExitReasons`, а он появился в API 30. На Android 10
  проверка невыполнима — подтверждено 26.08.2026: система ANR объявила, SDK на
  следующем старте сказал `No crashes detected`.

  Порядок: нажать кнопку, **стучать по экрану** (без ввода система не засечёт
  таймаут диспетчеризации), дождаться системного диалога и **закрыть приложение
  из него**. Закрыть обязательно: `REASON_ANR` система записывает, только если
  убивает процесс, пока главный поток ещё заблокирован. Кнопка держит поток две
  минуты именно для этого — раньше она отпускала через 10 секунд, процесс
  оживал, и отчёта не возникало.

ANR приходит только при `CrashReportConfiguration.setSendAnr(true)` — в примере
это выставлено в `TracerHostApplication`, в вашем приложении выставьте сами.

### 6.2 Загрузка символов Dart — эксперимент

Локальная часть уже доказана: утилита `dump_syms` **из самого плагина Tracer**
читает `app.android-arm64.symbols` и выдаёт 7545 функций с настоящими именами
Dart, против 0 у stripped `libapp.so`, под одинаковым MODULE id. Осталось
проверить, принимает ли и применяет ли это бэкенд.

```sh
../../../tool/prepare_dart_symbols.sh build/symbols

DART_SPLIT_DEBUG_INFO=$PWD/build/symbols/tracer-upload \
flutter build apk --release -Ptracer.enabled=true \
  --obfuscate --split-debug-info=build/symbols
```

`forceUploadNativeSymbols` больше **не** включается — правка от 27.08.2026 по
ответу вендора и разбору байткода. Подставной `libapp.so` разбирается как
`FULL`, поэтому его не выкидывает фильтр «нет полезных символов», а второй обход
(`additionalLibrariesPath`) удаляет из списка загрузки stripped-копию с тем же
(именем, build id) — так что на `nativesymbol/exists` под этой парой ничего
чужого уже нет. Флаг нужен только для починки: если под этот build id на бэкенд
уже уехал stripped `libapp.so`, проверка молча пропустит хорошие символы.
Собирайте со staging с первой же сборки данного build id — и такой ситуации не
возникнет.

Смотрите в логе сборки задачи загрузки символов и ответ сервера. Ищите строку
`Uploading libapp.so:<build-id>` — по одной на каждую архитектуру, с теми же
build id, что напечатал `prepare_dart_symbols.sh`. Строки «No usable symbols
found» про `libapp.so` быть не должно: она означала бы, что залился stripped,
а не подставной файл.

Ронять надо **кнопкой «Уронить процесс изнутри Dart (FFI)»**, а не соседней
«Уронить процесс нативно»: вторая поднимает сигнал из Kotlin, упавший поток
разматывается через libc и ART, и кадров внутри `libapp.so` в отчёте нет вовсе —
проверять было бы нечего.

- [x] 16: загрузка принята — 26.08.2026
- [x] 16: применение — **нет**, 27.08.2026. Отчёт: `libapp.so + 0xa5234`,
      build id `000…0`, тогда как настоящий адрес `0x155234`, а id

Опасение про `originalLibHash` снято 27.08.2026: вендор ответил, что
сопоставление идёт «как у minidump-stackwalk — по этим типаууидам от

### Проверка 20. Группировка переживает правку кода

По документации Tracer `crashId` считается из title и subtitle, а имя файла и
номер строки **не учитываются** — именно чтобы правка кода не разваливала
группу. Для нефатальных приоритет у `issueKey`, и он используется дословно,
поэтому наш синтетический ключ на iOS не содержит ни файла, ни строки.

Проверяется так:

1. Вызовите одну и ту же ошибку, дождитесь события, запомните группу.
2. Вставьте пустую строку выше по файлу, чтобы номер строки сдвинулся.
3. Пересоберите, вызовите ту же ошибку снова.

- [ ] 20: второе событие попало **в ту же группу**, что и первое — на Android и
  ```
  на iOS
  ```

Если разъехалось на iOS — в синтетический `issueKey` просочилось что-то
нестабильное. Если на Android — значит, в расчёт всё-таки попадает `fileName`
или `lineNumber` нашего `StackTraceElement`, и мапинг кадров надо менять.

**Для сборок со `--split-debug-info` эта проверка неприменима** — с
`--obfuscate` или без него: там в кадрах только адреса, и они смещаются от
сборки к сборке. Подробнее — в
[symbolication.md](symbolication.md).

## Если не приезжает

По убыванию частоты:

1. **Android, debug-сборка.** `setDebugUpload(true)` не выставлен. Самая частая
  причина «тишины».
2. **Не применён Gradle-плагин.** Наш плагин это ловит: в логах будет строка про
  отсутствующий ресурс `tracer_app_token`.
3. `resValues` **выключён.** С AGP 9 он выключен по умолчанию, и SDK падает в
  рантайме.
4. `isEnabled == false`**.** Посмотрите на экран примера: там выводится
  `enabled` и `backend`. `backend: unsupported` означает, что реализация под
   платформу не зарегистрировалась.
5. **Просто рано.** События появляются с задержкой; часть отправляется при
  следующем запуске приложения. Перезапустите и подождите.
6. **Токен не от того проекта.** У Android, iOS и JS проекты разные, токены
  тоже.
