[Карта документации](../README.md) и [команды проверки ссылок](../contributing.md#commands).

Можно выполнять независимо; новые результаты №24–29 добавлять после их приёмки,
не объявляя планируемое поведение уже реализованным.

## Контекст

`packages/apptracer_flutter/README.md` содержит около 700 строк: quick start,
платформенная настройка, troubleshooting, privacy, grouping, symbolication и
заметки конкретных релизов. RU/EN-версии дублируют большой объём. Актуальные
инструкции соседствуют с историческими ограничениями, а Runtime API 1.2.0
находится после раздела лицензии.

При этом acceptance-протоколы и датированные исследования ценны и должны быть
сохранены. Проблема не в их наличии, а в отсутствии ясной границы между текущим
руководством и историей проверок.

## Цель

Сократить путь нового пользователя до первого события, оставить один авторитетный
источник текущих версий/ограничений и сохранить исторические свидетельства без
путаницы.

## Сделать

1. Выделить в package README короткий сценарий: установка → настройка выбранной
   платформы → `Tracer.initialize` → тестовое событие → ссылки на troubleshooting.
2. Вынести подробные разделы в тематические руководства: Android, iOS, web,
   desktop, consent/privacy, filtering/custom context, symbolication. Не дублировать
   полный текст между root/package/platform README.
3. Сделать `docs/platform-matrix.md` единственной сводной таблицей текущих версий,
   поддерживаемых сред и ограничений. Из README ссылаться на неё вместо повторения
   меняющихся номеров там, где это не мешает минимальному примеру.
4. Переместить release-specific Runtime API и старые migration notes в хронологию
   релизов/миграций. Лицензию и текущие ссылки вернуть в предсказуемый конец README.
5. Пометить датированные status/acceptance/audit документы как исторические
   свидетельства с областью проверки. Не удалять их и не переписывать задним
   числом под текущее поведение. Массово перемещать файлы без необходимости не надо.
6. Синхронно обновить RU/EN README и затронутые ссылки. Сохранить существующие
   внешние anchors либо оставить совместимые якоря/ссылки.
7. Добавить лёгкую проверку локальных Markdown-ссылок и anchors для изменённых
   документов, включая documentation-only PR. Не запускать тяжёлые кодовые
   workflows только ради Markdown.
8. Провести финальную сверку с `docs/status.md`, publishing и текущими pubspec:
   опубликованные версии, непроверенные платформы и внешние дефекты не должны
   противоречить друг другу без пояснения даты.

## Критерии приёмки

- Новый пользователь находит минимальную установку и проверку первого события без
  чтения истории релизов.
- Каждая платформа имеет одно актуальное основное руководство; общие версии и
  ограничения не дублируются в нескольких расходящихся местах.
- RU/EN quick start описывает одинаковое поведение и не содержит устаревших
  «не опубликовано»/«платформа не поддерживается» утверждений.
- Датированные протоколы сохранены и явно отличаются от текущей документации.
- Все новые и изменённые локальные ссылки/anchors проходят автоматическую проверку;
  внешние ссылки на основные инструкции сохранены.
- Документация описывает только фактически реализованное и проверенное поведение.

## Проверки

- Пройти quick start по документу в чистом example без использования старого
  контекста: Android/iOS/web — по доступности, desktop — по существующей инструкции.
- Запустить Markdown link/anchor checker на documentation-only изменение.
- Сверить RU/EN diff по смыслу и номерам версий, pubspec и `docs/status.md`.
- Убедиться, что `./tool/check.sh` не требуется для docs-only PR, а docs workflow
  завершается успешно.

## Не входит

- Переписывание исторических acceptance-результатов.
- Документирование планируемых retry, Pigeon или новых SDK как уже выпущенных.
- Массовое переименование документов ради единой структуры каталогов.
