# П. 25. Надёжность Web/HTTP-доставки

**Статус:** реализация и VM/Chrome/release-loopback проверки завершены; live Tracer smoke не выполнен. **Приоритет:** P0. **Сложность:** XL.

[Политика доставки, ограничения и протокол проверок](../web-protocol.md#надёжность-доставки).

Связанный общий план: [development_v1.md](development_v1.md).
Можно выполнять независимо от [№24](task-24-android-event-context.md) и
[№26](task-26-flutter-version-ci.md).

## Контекст

`TracerHttpTracer.recordError` выполняет один HTTP POST без таймаута. Сетевая
ошибка перехватывается и только логируется; событие не сохраняется и не
повторяется. Любой статус ниже 400 записывается в debug-лог как `uploaded`, но
`200 {"success":true}` не доказывает, что Tracer принял полезную нагрузку.

Текущее ограничение уже описано в `docs/privacy.md`: Web/HTTP не имеет
persistent queue и retry. Простое добавление повторов без ограничений создаст
риски дублей, роста хранилища и отправки данных после отзыва согласия.

Основные места:

- `packages/apptracer_flutter_http/lib/src/tracer_http_tracer.dart:135`;
- `packages/apptracer_flutter_http/lib/src/tracer_batch_item.dart`;
- `packages/apptracer_flutter_http/test/collection_lifecycle_test.dart`;
- `packages/apptracer_flutter_web/lib/apptracer_flutter_web.dart`;
- `docs/web-protocol.md` и `docs/privacy.md`.

## Цель

Не терять допустимые к отправке события при временном отсутствии сети и при этом
сохранить ограничения приватности, предсказуемый расход хранилища/трафика и
безопасный lifecycle.

## Сделать

1. Зафиксировать политику доставки: какие ошибки считаются временными, сколько
   раз и как долго повторять запрос, какой TTL и максимальный объём очереди,
   что делать при переполнении. Не повторять бездумно постоянные 4xx.
2. Добавить конечный таймаут запроса и экспоненциальный backoff с jitter.
   Учитывать `Retry-After` для 429 и не создавать параллельные штормы отправок.
3. Ввести тестируемую абстракцию хранилища и браузерную реализацию на IndexedDB.
   Очередь должна быть ограничена по числу/байтам и TTL; поведение при запрете
   хранилища — явное и проверенное.
4. Сохранять только события, разрешённые текущей сессией сбора. При
   `stopAndClearCollection` синхронно закрыть приём новых событий, отменить
   собственные повторы и удалить очередь, логи, ключи и userId.
5. Проверить восстановление после перезагрузки страницы: разрешённая очередь
   отправляется повторно, отозванная — никогда. Не включать сбор только ради
   обработки очереди до решения приложения о согласии.
6. Исследовать доступный в ingest идентификатор события/идемпотентность.
   Предотвратить автоматические дубли там, где протокол это позволяет; если
   подтверждение потеряно после принятия сервером, честно описать оставшийся риск.
7. Добавить необязательную диагностику состояний `queued/sent/retry/dropped/failed`
   без персональных данных и без ломающего изменения существующего `Future<void>`
   API. Не выдавать возврат HTTP-вызова за гарантию появления события в консоли.
8. Сверять наблюдаемый wire protocol с актуальным JS SDK вендора и обновить
   contract fixtures. Рассмотреть JS interop только отдельным обоснованным
   решением; не менять транспорт одновременно с внедрением очереди.
9. Обновить RU/EN-документацию: retry, хранение, потерянные события, дубли,
   очистка и границы подтверждения доставки.

## Критерии приёмки

- Offline → online доставляет сохранённое событие в допустимой сессии без
  ручного повторного `recordError`.
- Таймаут, разрыв соединения, 429 и выбранные 5xx повторяются по политике;
  постоянные 4xx не зацикливаются.
- Очередь переживает перезагрузку, не превышает лимиты и удаляет просроченные
  элементы. Переполнение и запрет IndexedDB видны в диагностике.
- Stop/clear предотвращает позднюю отправку и удаляет собственную очередь;
  повторный старт не восстанавливает отозванные данные.
- Повторная обработка подтверждённого события не создаёт автоматических дублей
  либо ограничение протокола явно задокументировано и покрыто тестом.
- VM и Chrome-тесты проходят; release web-сценарий проверен через реальный
  браузер и loopback. Live Tracer-проверка отдельно фиксирует отображение события,
  а не только HTTP 200.

## Проверки

- Unit-тесты с fake clock, injectable HTTP client и хранилищем: retry schedule,
  TTL, переполнение, malformed records, конкурентные stop/start.
- `flutter test` и `flutter test --platform chrome` для HTTP/web-пакетов.
- Release browser acceptance: offline, reload, recovery, stop/clear и новая сессия.
- `./tool/check.sh`; данные очередей и токены не включать в отчёты/артефакты.
