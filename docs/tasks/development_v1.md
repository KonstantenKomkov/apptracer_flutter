### Порядок и правила

1. Windows и macOS отправляют данные в **Tracer** через официальный Sentry SDK и DSN
   из Tracer. Для Ubuntu/Linux проверить этот же путь в №1 и №13, включая нативный
   backend и совместимость приёмника. Аврора использует нативный Tracer SDK.
   Поддержка Ubuntu не означает поддержку всех дистрибутивов Linux.
2. Сохранить единый публичный `Tracer` API и федеративную архитектуру. Изменения общих
   моделей и зависимостей проверять также на Android, iOS и Web.
3. В desktop не включать одновременно старый ручной HTTP-транспорт и новый SDK.
   Ручной транспорт удалён. Для прежних Git- и path-потребителей сохранена
   [инструкция по переходу](../desktop-migration.md#moving-from-the-manual-transport).
4. Правила `appRunner` ровно один раз, сохранение чужих обработчиков ошибок, отсутствие
   дублей и безопасный отказ при ошибке инициализации сохраняются на новых платформах.
5. Выполнение кода, успешная сборка, доставка события и символизация — отдельные результаты.
   Нельзя закрывать платформенную приёмку только по тестам или HTTP-ответу приёмника.
6. Для каждой задачи выполнить ревью изменений, устранить найденные проблемы и записать
   проверки. Невыполненную внешнюю приёмку оставить открытой с конкретным блокером.
7. Рабочие DSN и токены не помещать в план и примеры. Plugin token нужен инструментам
   загрузки символов и не должен попадать в поставляемое приложение.

## П. 11. Сквозная приёмка Windows, macOS, Ubuntu и Авроры в Tracer

**Прогресс 23 октября 2026:** после lifecycle-коммита `a373234` выполнены две
live smoke-серии и два native crash/restart в проект `Test` с метками
`macos-check-aa68494c5c-{dart,native}`. Пользователь показал четыре группы,
FATAL/ERROR и заголовки новой Dart-сборки. В новой native-карточке подтверждены
userId, custom keys, breadcrumb (точное время второй пробы), macOS/arm64,
release/build/UUID и `handled=false`/signal. Агент затем сам сверил в консоли все
12 карточек: в каждой из четырёх групп два новых события и одно старое, всего
8 новых без дублей/потерь. В свежем FlutterError подтверждены метка, breadcrumb
и Dart Context. Эта live-серия пройдена; [протокол и event IDs](../macos-lifecycle-acceptance.md).
№11 целиком не закрывается: остаются расширенная macOS-матрица и Аврора.

**Выполнено для Ubuntu:** проверенная live-серия с Dart/native source frames,
полями, группировкой, clear/restart и сменой аккаунта перенесена в
[№11.Ubuntu-live](development_completed_v1.md#task-11-ubuntu-live).
Offline/revoke/in-flight подтверждены отдельными VM/loopback/CI-сценариями №8/13;
их не следует описывать как новые live-пробы. Внешняя release-проверка закрыла
фильтрацию/дедупликацию; метрики и статус/матрица согласованы.
[Ubuntu-объём №11 завершён](development_completed_v1.md#task-11-ubuntu).

**Выполнено для Windows 11 x64:** 24 локальных release-сценария, восемь
live-событий существующего C/C++ Test, три вида Dart и native source frames,
поля, grouping counts 3/2 и 1/1, account isolation после clear/restart,
filtering/dedup двух внешних consumer. [№11.Windows](development_completed_v1.md#task-11-windows).

На чистой Windows 11 x64 VM прошли 11 runtime/consumer-проверок, в CI — 24 сценария. Windows 10 и ARM64 остаются за пределами приёмки.

**Контекст.** Новый проект позволяет проверить реальные события; прежняя документация
репозитория не содержит такой проверки для этих платформ.

**Сделать.**

1. Выполнить матрицу на release-сборках: ручная ошибка, FlutterError, unhandled async,
   нативное падение без отладчика, новый запуск, offline → online, start/stop/clear.
   На Авроре неподтверждённые Dart-возможности из №7 сохраняются как блокеры.
   Ubuntu VM/X11 и внешние потребители уже приняты; их результаты не считать
   проверкой Авроры или других Linux-дистрибутивов.
2. В консоли проверить проект, ОС, версию, тип/fatal, количество событий, группировку,
   исходный/восстановленный стек, breadcrumbs, ключи и userId; повторить после удаления данных.
3. Проверить фильтрацию и отсутствие дублей. Не считать Dart unhandled error завершением

4. Сохранить протокол: дата, версии инструментов, ОС/архитектура, commit, команды,

5. Обновить `docs/status.md` и `docs/platform-matrix.md` фактическими результатами.

**Критерий приёмки.** Для каждой заявленной платформы есть событие в Tracer и полный
протокол её сценариев. Неудачи не скрыты успешной сборкой; общая приёмка остаётся открытой,

   матрицу платформ: RU/EN README пакетов/примеров, symbolication, ограничения
   native/Dart, lifecycle и дополнительных данных SDK. Сохранить подтверждённые
   результаты и принятые ограничения macOS/Ubuntu. Статус, матрица и вводный
   Ubuntu-протокол уже согласованы с принятыми результатами.
2. Определить финальные версии и changelog, зависимости и порядок публикации
   изменённых пакетов. Для Авроры описать установку в поддерживаемой экосистеме
   и проверить допустимость её платформенных метаданных для выбранного канала.
3. Выполнить применимые проверки состава/dry-run и внешних потребителей для
   остальных выпускаемых платформ; проверить отсутствие plugin token в их
   артефактах. Для финального release-кандидата повторить применимые проверки
   после изменений версий/зависимостей.
4. Сохранить различие между подготовленным кандидатом, проверкой path/git
   зависимости и установленной опубликованной версией. Публикация выполняется
   отдельным действием; после неё проверяется hosted desktop-потребитель.

**Критерий приёмки оставшейся части.** Подготовлен проверяемый комплект выпуска
и документация для всех принятых платформ; установка и ограничения воспроизводимы.
Непринятые возможности не объявлены поддержанными, публикация не отмечена
выполненной без фактического выпуска.
