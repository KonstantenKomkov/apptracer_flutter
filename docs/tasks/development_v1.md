### Порядок и правила

1. Windows и macOS отправляют данные в **Tracer** через официальный Sentry SDK и DSN
   из Tracer. Для Ubuntu/Linux проверить этот же путь в №1 и №13, включая нативный
   backend и совместимость приёмника. Аврора использует нативный Tracer SDK.
   Поддержка Ubuntu не означает поддержку всех дистрибутивов Linux.
2. Сохранить единый публичный `Tracer` API и федеративную архитектуру. Изменения общих
   моделей и зависимостей проверять также на Android, iOS и Web.
3. В desktop не включать одновременно старый ручной HTTP-транспорт и новый SDK.
   Существующий `apptracer_flutter_sentry` сейчас формирует envelopes самостоятельно,
   зависит от `http` и имеет `publish_to: none`; подключение DSN к нему не закрывает №2.
4. Правила `appRunner` ровно один раз, сохранение чужих обработчиков ошибок, отсутствие
   дублей и безопасный отказ при ошибке инициализации сохраняются на новых платформах.
5. Выполнение кода, успешная сборка, доставка события и символизация — отдельные результаты.
   Нельзя закрывать платформенную приёмку только по тестам или HTTP-ответу приёмника.
6. Для каждой задачи выполнить ревью изменений, устранить найденные проблемы и записать
   проверки. Невыполненную внешнюю приёмку оставить открытой с конкретным блокером.
7. Рабочие DSN и токены не помещать в план и примеры. Plugin token нужен инструментам
   загрузки символов и не должен попадать в поставляемое приложение.

и исходным файлом там, где формат это поддерживает, а также точная привязка к сборке.

## П. 6. Нативный плагин Tracer для Авроры

**Прогресс 23 октября 2026:** подготовлены загрузка SDK 0.1.15 с проверкой ZIP и
всех файлов, ELF ABI/build-id manifest, CMake imported target для aarch64/x86_64,
проверка сигнатур header и диагностическая утилита загрузки без init/upload.
На macOS собраны C++-инструменты и прошли 7 host-тестов; Ubuntu CI также прошёл
загрузку поставки, C++-сборку и 7 тестов (прогон `39992802784`).
Отдельно проверены экспортируемые функции и ELF-зависимости трёх архитектур:
OpenSSL 1.1.0/1.1.1 и GLIBC вплоть до 2.38; добавлена воспроизводимая проверка.
Расширенный Ubuntu CI `39996142549` прошёл и эту проверку.
[Команды и ограничения](../aurora-preparation.md). Flutter-плагин, runner и RPM
ещё не реализованы. Нужны Aurora toolchain/embedder и решение ограничений B5;
№6 не архивируется, host-проверки не заменяют целевую сборку и запуск.

**Контекст.** Нужен отдельный адаптер для Flutter embedder Авроры. По
[инструкции Tracer](https://apptracer.ru/doc/native-aurora/quick-start/) нативная
поставка содержит `libtracernative.so` и `tracer.h`; системные минидампы создаёт `crash-dumper`.

**Сделать.**

1. Создать платформенный пакет Авроры и минимальный runner на поддерживаемом embedder.
   Зафиксировать способ регистрации без ошибочного включения на обычном Linux.
2. Подключить закреплённую нативную поставку, include/link и установку библиотеки
   для выбранных архитектур. Проверить источник, контрольную сумму и условия поставки SDK.
3. Адаптировать сборочную систему runner; qmake-пример вендора не считать готовым
   рецептом для другого embedder. Проверить состав устанавливаемого RPM и загрузку `.so`.
4. Реализовать согласованный старт с app token, постоянным каталогом SDK и версией приложения.
   Использовать сбор минидампов из cache и загрузку отчётов прошлого запуска по API вендора;
   запуск и загрузку подчинить состоянию сбора из №8.
5. Проверить системные зависимости и права. Недоступная библиотека, каталог или
   `crash-dumper` должны давать понятную диагностику, не препятствуя запуску Flutter.

**Критерий приёмки.** RPM устанавливается и запускается в целевой среде,
нативный плагин доступен из Dart; тестовое падение создаёт отчёт и после разрешённого
повторного запуска появляется в Tracer. Есть версия ОС/embedder и архитектура проверки.

## П. 7. Связать Dart API с нативным Tracer на Авроре

**Входной риск из №1:** в проверенном header 0.1.15 нет API передачи Dart
type/message/stack и удаления ключа; non-fatal dump требует Crashpad. См.
[аудит API](../desktop-aurora-sdk-audit.md#проверка-поставки-авроры), блокер B5.
Нужен подтверждённый путь у вендора; лог или искусственный crash не закрывает пункт.

**Контекст.** Нативный crash runner и исключение Dart — разные события.
Минидамп сам по себе не обеспечивает поддержку `Tracer.recordError`.

**Сделать.**

1. Реализовать мост `TracerPlatform` к нативному плагину: состояния, логи, ключи,
   версия и доступные операции пользователя на основе проверенного в №1 заголовка.
2. Проверить supported API для non-fatal/Dart-событий. Сохранить тип, сообщение и исходный
   стек; не превращать обработанное исключение Dart в искусственное падение процесса.
3. Если нужного нативного API нет, записать блокер и отдельное решение по расширению
   поддержки. Не выдавать запись в лог за доставленную Dart-ошибку и не подменять
   запрошенную нативную интеграцию незаметным HTTP/Sentry fallback.
4. Проверить breadcrumbs и ключи в отчёте нативного падения; обеспечить очистку удалённых
   ключей и userId либо явно вернуть ограничение, если SDK этого не позволяет.
5. Проверить Unicode, большие сообщения и повторные вызовы через границу Dart/native.

**Критерий приёмки.** Публичные операции имеют подтверждённое отображение на нативный SDK.
Поддержка Dart-ошибок подтверждена отдельным событием в Tracer либо остаётся открытым
блокером; нативные падения, логи и ключи проверены независимо.

## П. 8. Запуск, остановка и очистка сбора на новых платформах

**Выполнено:** [№8.macOS](development_completed_v1.md#task-8-macos) — 55 шагов
lifecycle на arm64; [№8.Ubuntu](development_completed_v1.md#task-8-ubuntu) —
18-шаговый lifecycle и отдельные retry/revoke/discard/in-flight сценарии.
Для Ubuntu актуален backend `native` с остановкой собственного `sentry-crash`;
прежний Crashpad распознаётся для очистки старой очереди. На обеих платформах
повторное включение после native init требует нового процесса.
Windows lifecycle также [архивирован](development_completed_v1.md#task-8-windows).
Общая №8 остаётся открытой для Авроры; следующие критерии относятся
к их оставшейся реализации и приёмке.

**Windows, самостоятельная проверка 23 октября:** в CI `40003238550` подтверждено
восстановление native minidump после HTTP 503, остановки старого Crashpad и нового
запуска с сохранением отчётов. SHA-256 принятого и отклонённого дампа совпадает,
принят ровно один отчёт. [Протокол](../windows-native-acceptance.md).
Это историческая проверка. Текущий native backend, stop/clear, отзыв replay
и смена аккаунта приняты отдельно 24 октября; см. №8.Windows в архиве.

**Входной риск из №1:** `tracer_disable_upload` в Aurora 0.1.15 не обещает
shutdown/purge; `tracer_upload_async` использует detached thread без handle отмены.
Нужно доказать остановку writer/uploader и очистку системных dumps либо сохранить
блокер B5. У Sentry `close` также не доказывает очистку cache; проверка B7 обязательна.

**Контекст.** В проекте уже есть deferred initialization, `startCollection`,
`stopCollection`, `stopAndClearCollection`, `preservePreviousReports` и состояния
`restartRequired`/`unsupported`. Новый SDK не должен обходить этот контракт.

**Сделать.**

1. Для каждой платформы проверить отсутствие инициализации и отправки до разрешённого
   старта, включая native bootstrap, восстановление очереди и регистрацию плагина.
2. Реализовать последовательные start/stop, повторные вызовы и отмену незавершённого старта.
   Возвращать фактическое состояние SDK; не сообщать `disabled`, если очистка не удалась.
3. Проверить очистку offline-очереди, файлов crash, логов, ключей и userId; после нового
   старта не отправлять данные отозванной сессии. Учесть уже начатые сетевые запросы.
4. Для Авроры отдельно проверить системные dumps, создаваемые вне каталога SDK:
   запрещённый период не должен импортироваться при последующем разрешённом запуске.
5. Проверить crash после stop и следующий запуск, смену пользователя и сохранение
   разрешённых отчётов при обычном перезапуске. Если SDK требует рестарта, вернуть
   `restartRequired` и проверить поведение следующего процесса.
6. Дополнить тесты жизненного цикла и провести нативные сценарии на каждой ОС.

**Критерий приёмки.** Для Windows, macOS, Ubuntu и Авроры есть результаты start/stop/clear,
offline/restart и смены пользователя. Неочищаемые данные или обход запрета сбора —
блокер поддержки платформы, а не успешно завершённая задача.
