# Обновление Android до Tracer SDK 1.6.1

План от 10 ноября 2026. Цель — обновить Android-интеграцию apptracer_flutter,
использовать Maven Central и проверить изменения runtime и Gradle-плагина.
Android №13–15 завершены; №16–22 открыты. Номера исходного плана сохранены;
общий №13 уже занят Ubuntu, поэтому архив Android использует отдельные якоря.
Связь с [общим бэклогом](development_v1.md).
Завершённые пункты переносить в [общий архив](development_completed_v1.md),
сохраняя номера, результаты проверок и ссылки.

## Основание и текущая интеграция

Основание — предоставленный пользователем анонс SDK 1.6.1 и дополнение о
публикации в Maven Central. Повторы и повреждённые фрагменты анонса исключены.
Релиз заявляет `Tracer.enable`, изменение ограничений воркеров `runNow`,
`HeapDumpsConfiguration.Builder.provideEnabled`, изменение генерации `buildUuid`,
исправления configuration cache и обработки mappings в
`AnalyticsEnabledApplicationVariant`.

- Android-пакет компилируется и тестируется с SDK 1.5.2; пример использует BOM
  и Gradle-плагин 1.5.2. SDK подключает приложение через `compileOnly` в плагине.
- Репозиторий VK прописан в Android-пакете и в обоих контурах разрешения
  зависимостей примера: `pluginManagement` и обычные repositories.
- `Sdk140ConsentRuntime` принимает только 1.4.0 и 1.5.2. Остановка управляемого
  SDK отзывает исполнители, удаляет данные, отключает native writer и watchdog;
  повторный старт после такой остановки требует перезапуска процесса.
- В общем Dart API уже есть `startCollection`, `stopCollection` и состояния
  `enabled`, `disabled`, `restartRequired`, `unsupported`, `error`.
  Методы HeapDumps/DiskUsage в нём отсутствуют; эти модули пример не подключает.
- В `app/tracer.gradle` сейчас указано `uploadMapping = true` и обязательны оба
  токена. Название `uploadMappings` из анонса нужно сверить с DSL версии 1.6.1.

Контекст: [аудит 1.5.2](../android-sdk-1.5.2.md),
[контракт управления сбором](../native-collection-consent.md),
[символизация](../symbolication.md).

## Общие правила

1. Сохранить федеративную архитектуру и подключение SDK приложением. Не включать
   дополнительные диагностические модули по умолчанию ради обновления версии.
2. Сначала использовать существующий Dart lifecycle API. Расширение публичного
   API HeapDumps/DiskUsage требует отдельного решения после проверки нативного API.
3. Build-time disable, отсутствие SDK, deferred-старт и runtime disable — разные
   состояния. `Tracer.enable` не инициализирует SDK, отключённый при сборке.
4. Возобновление через `enable` само по себе не доказывает возможность повторного
   старта после полной очистки. Сохранять `restartRequired`, где это необходимо.
5. Для каждой задачи провести ревью и записать применимые проверки. Разделять
   компиляцию, JVM-тесты, runtime, доставку и символизацию в Tracer.
6. CI-проверки сборки выполнять без живой загрузки mappings/символов. Live-приёмка
   использует отдельную конфигурацию; секреты не включать в отчёты и артефакты.

## П. 16. Проверка HeapDumps.runNow и DiskUsage.runNow

**Сделать.** Подготовить отдельную нативную конфигурацию примера для опциональных
модулей. Проверить оба `runNow` при отключённой зарядке и без сети: у создаваемых
воркеров нет требований сети/зарядки, постановка WorkManager асинхронная.
По аудиту №13 `HeapDumps.runNow(tag)` синхронно создаёт hprof: host-обёртка
должна вызывать его вне UI-потока; не обещать отсутствие VM-пауз при дампе.
Отделить выполнение диагностики от последующей доставки её результата.

Проверить отсутствие блокировки UI, поведение повторных запросов и запрет
диагностики до разрешения/после отзыва. Аудировать WorkManager-задачи этих
модулей: управляемые исполнители crash-модуля могут не контролировать их.
Не распространять изменение `runNow` на периодические задачи без проверки.

**Приёмка.** Для каждого метода есть проверка constraints и runtime-протокол
без зарядки/сети; доставка проверена отдельно после восстановления сети.
Нет обещания мгновенного или синхронного завершения: запуск зависит от Android.
Если отзыв/очистка этих модулей не обеспечены, они явно исключены из
поддерживаемого deferred-режима и не подключены к нему по умолчанию.

## П. 17. Ленивое включение HeapDumps

**Сделать.** Добавить нативный пример `HeapDumpsConfiguration.Builder.provideEnabled`
в host-конфигурации опционального модуля. Проверить момент, поток и частоту
вызова провайдера, обработку исключений и совместимость с обычным `enabled`.
Не считать ленивый провайдер динамической подпиской на изменения значения.

Проверить false/true и решение, полученное после создания builder, но до
фактического чтения провайдера. Согласовать момент чтения с deferred-стартом;
провайдер не должен обходить общий запрет сбора. Проверить custom
`HasTracerConfiguration`, которому принадлежит конфигурация SDK.

**Приёмка.** Пример показывает отложенное решение без раннего вычисления;
тесты фиксируют фактическую семантику провайдера. Документированы границы
изменения значения после инициализации. HeapDumps остаётся опциональным.

<a id="task-18"></a>

## П. 18. Управление mappings и генерацией buildUuid

**Сделать.** Ввести явную настройку загрузки mappings в примере, используя
подтверждённое в №13 имя DSL. Разделить управление mapping и native symbols.
Требовать plugin token только для включённых операций, которым он нужен;
сохранить проверку app token для рабочего SDK.

Проверить матрицу R8-обфускация on/off × загрузка mappings on/off. Ожидаемое
по анонсу поведение: `buildUuid` создаётся и встраивается только при включённых
обфускации и загрузке mappings. Исследовать генерируемые ресурсы, APK и граф
задач; отключённая загрузка не должна выполнять upload-запросы.

**Приёмка.** Все четыре комбинации проверены, включая значение загрузки по
умолчанию отдельно от явного false. Две чистые одинаковые сборки с отключённой
загрузкой не отличаются из-за Tracer `buildUuid`; это не объявляется доказательством
полной побайтовой воспроизводимости APK. CI может собирать SDK без plugin token,
когда обе загрузки отключены. Продакшен-конфигурация сохраняет нужные загрузки.

<a id="task-19"></a>

## П. 19. Регрессия Gradle configuration cache

**Сделать.** Добавить воспроизводимую проверку: два запуска одной сборочной
команды с `--configuration-cache --configuration-cache-problems=fail`, без
очистки между ними. Проверять сборку с Tracer и контрольную без него.
В Tracer-конфигурации использовать отключённые внешние загрузки из №18.

После успешного повторного использования кеша изменить значимый вход
конфигурации, например флаг mappings, и проверить корректную инвалидацию.
Убедиться, что provider-based чтение настроек и новые ветки Gradle-скриптов
совместимы с кешем. Разделить ошибки Tracer и ограничения Flutter/AGP.

**Приёмка.** Второй запуск явно сообщает reuse configuration cache; изменение
входа приводит к пересчёту и корректному результату. Команды и версии записаны,
CI проверяет этот сценарий. Если полный Flutter build блокирует чужая задача,
есть минимальный Android reproducer и отдельный открытый блокер полной сборки.

## П. 21. Сквозная приёмка Android 1.6.1

**Сделать.** Прогнать существующие Android JVM, Flutter/channel и lifecycle-тесты,
проверки `tool/check_sdk140*`, release/R8 с SDK и без SDK. При изменениях общих
пакетов выполнить затронутые регрессии других платформ.

На release-сборке проверить automatic/deferred, build-time disable, runtime
disable/enable, stop/clear, offline/in-flight, смену пользователя и новый процесс.
Проверить Dart-ошибку, Java/Kotlin crash, native crash и ANR; для tombstone —
API 31+ с opt-in и контрольный сценарий без него. Сохранить приоритет purge
над `preservePreviousReports` и исключить отправку данных отозванной сессии.
Повторить применимые проверки опциональных модулей из №16–17.

**Приёмка.** Есть протокол с SDK/toolchain/API level, commit и идентификаторами
событий. В Tracer подтверждены доставка, отсутствие дублей, поля и Java/Kotlin
символизация точной minified-сборки. Непройденные device/live-сценарии остаются
открытыми с конкретным блокером; результаты 1.4.0/1.5.2 не выдаются за 1.6.1.
