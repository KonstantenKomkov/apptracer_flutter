# П. 28. Единые локальные проверки и сводный coverage

**Статус:** выполнена. **Приоритет:** P1. **Сложность:** M.

[Каталог и команды](../contributing.md#commands): `tool/packages.tsv` управляет локальными проверками, CI и publish dry-run. Сводный coverage и baseline описаны там же.

Связанный общий план: [development_v1.md](development_v1.md).
Зависит от немутирующего analyze в [№26](task-26-flutter-version-ci.md).

## Контекст

Проверки распределены между несколькими списками:

- `tool/check.sh` не включает `apptracer_flutter_desktop`;
- `Makefile` analyze/test запускает только facade и его example;
- основной CI перечисляет собственную матрицу пакетов;
- desktop и нативные acceptance запускаются отдельными workflow;
- coverage сохраняется отдельными `lcov.info` без агрегированного результата.

Из-за этого комментарий «всё, что гоняет CI» неточен, а локальный зелёный прогон
может оставить desktop или нативные контракты непроверенными. Тяжёлые runtime
сценарии при этом не должны незаметно становиться обязательными для каждого
локального запуска.

## Цель

Сделать состав проверок предсказуемым, устранить расхождение списков и показывать
покрытие критичного Dart-кода без формального погони за процентом.

## Сделать

1. Создать единый каталог пакетов с метаданными: путь, publishable/unpublished,
   вид unit-тестов, необходимость Chrome, наличие native/desktop jobs. Выбрать
   простой формат, который могут читать shell/Make/CI без лишней инфраструктуры.
2. Использовать каталог в `tool/check.sh`, Makefile и CI matrix/publish dry-run.
   Убрать расхождения в комментариях: локальный скрипт либо действительно повторяет
   доступные CI-проверки, либо явно называет пропущенные платформенные этапы.
3. Включить desktop analyze/unit tests в базовый локальный check на поддерживаемой
   ОС. macOS/Windows/Linux native acceptance оставить в профильных workflow и
   отдельных явных командах.
4. Сделать `make analyze` и `make test` полными по заявленному набору либо удалить
   дублирующие цели в пользу понятных `make check`/`make check-unit`.
5. Сохранять запуск всех доступных пакетов после отказа одного и возвращать
   ненулевой итог. В конце печатать краткую сводку passed/failed/skipped.
6. Собрать общий coverage report по Dart-пакетам и публиковать HTML/JSON/lcov как
   один артефакт. Исключить generated files и examples из знаменателя осмысленно,
   не скрывая production code.
7. Зафиксировать baseline и отслеживать изменение покрытия для parser,
   `TracerClient`, lifecycle и HTTP transport. Не вводить жёсткий общий порог до
   анализа текущих непокрытых веток; targeted thresholds можно задать отдельно.
8. Обновить `docs/contributing.md` и README: какие команды быстрые, какие полные,
   что требует устройство/ОС/Chrome и где лежат результаты.

## Критерии приёмки

- Один каталог определяет список пакетов для локального скрипта и CI; добавление
  нового пакета не требует синхронной правки нескольких независимых списков.
- `make check` проверяет все доступные Dart-пакеты, включая desktop, и явно
  сообщает о нативных/runtime проверках, которые не запускались.
- Форматирование, analyze, unit tests и publish dry-run выполняются для заявленного
  набора; ошибка одного пакета не скрывается последующими успешными командами.
- CI публикует единый coverage summary; по критичным файлам видно изменение относительно
  baseline. Coverage не считается доказательством live-доставки.
- Команды не изменяют отслеживаемые исходники и не оставляют неигнорируемых отчётов.

## Проверки

- `./tool/check.sh`, `make analyze`, `make test`, `make check`.
- Прогон с намеренно сломанным одним пакетом в отдельной временной ветке/worktree:
  остальные проверки выполняются, итоговый статус ненулевой. Не оставлять такое
  изменение в основной рабочей копии.
- Проверить web tests с Chrome и корректный явный failure при его отсутствии.
- Проверить desktop unit tests локально, а platform workflows — в GitHub Actions.
- `git status --short` после всех команд.

## Не входит

- Обязательный запуск тяжёлых device/live сценариев на каждый `make test`.
- Публикация пакетов или запуск с реальными токенами.
- Искусственное повышение coverage тестами без проверки поведения.
