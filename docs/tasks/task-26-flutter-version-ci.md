# П. 26. Матрица версий Flutter и немутирующие проверки CI

**Статус:** открыта. **Приоритет:** P1. **Сложность:** M.

Связанный общий план: [development_v1.md](development_v1.md).
После этой задачи стандартные проверки должны оставаться воспроизводимыми для
[№28](task-28-unified-checks-coverage.md).

## Контекст

Пакеты заявляют Flutter `>=3.22.0`, но основной `.github/workflows/ci.yml`
использует 3.35.7, а desktop workflow — 3.47.4. Минимальная заявленная версия и
актуальный stable в одном общем контуре не проверяются.

При локальном запуске Flutter 3.47.4 `flutter analyze` автоматически дописал
platform/build `exclude` в восемь `analysis_options.yaml`. Последующий
`dart pub publish --dry-run` увидел modified files и завершился с предупреждением.
После удаления автоматических правок все семь dry-run прошли. Нужно устранить
причину, а не игнорировать dirty tree.

## Цель

Регулярно проверять заявленный минимум и новый stable, заранее замечать
несовместимость и гарантировать, что стандартные команды не изменяют исходники.

## Сделать

1. Добавить отдельный job для минимального Flutter 3.22.0 / соответствующего
   Dart. Покрыть analyze и unit-тесты общих пакетов; платформенные сборки
   добавлять только там, где старый toolchain поддерживается runner image.
2. Добавить latest-stable canary для основных пакетов и desktop unit-тестов.
   Для обычных PR сохранить воспроизводимую закреплённую версию; обновление pin
   выполнять отдельным проверяемым изменением.
3. Централизовать версии toolchain там, где GitHub Actions позволяет это без
   дублирования всего workflow. Зафиксировать, какие версии являются поддерживаемым
   baseline, а какие — диагностическим canary.
4. Зафиксировать требуемые `analyzer.exclude` во всех пакетах и examples, включая
   существующие native platform directories. Не исключать исходники `lib`/`test`.
5. Добавить в проверки `git diff --exit-code` и контроль untracked-файлов после
   analyze/test/build там, где это практично. Ожидаемые build outputs должны
   игнорироваться; изменения исходников — нет.
6. Настроить автоматические PR для Flutter baseline и GitHub Actions через
   Dependabot/Renovate. Sentry candidate-обновления не смешивать с этой задачей:
   их принимает [№29](task-29-desktop-sentry-upgrades.md).
7. Убедиться, что path filters запускают нужную матрицу при изменении shared
   interface, facade, native adapters, tooling и самих workflow.
8. Обновить `docs/contributing.md` и `docs/platform-matrix.md`: заявленная
   совместимость отличается от фактически проверенных версий.

## Критерии приёмки

- Минимальный заявленный Flutter и закреплённый текущий baseline проходят
  применимые analyze/test/build проверки.
- Latest-stable canary работает по расписанию и на изменения toolchain; его
  падение даёт отдельный понятный сигнал, а не подменяет baseline.
- `flutter analyze` и `./tool/check.sh` на поддерживаемых версиях не изменяют
  отслеживаемые файлы.
- Publish dry-run выполняется на чистом дереве и не падает из-за файлов,
  автоматически изменённых предыдущим шагом.
- Изменения в общих пакетах запускают все зависимые проверки, включая desktop,
  где это требуется.
- CI не требует живых токенов Tracer и не публикует пакеты автоматически.

## Проверки

- Локально: `./tool/check.sh`, затем `git status --short` и `git diff --check`.
- Отдельно прогнать минимальный Flutter через выбранный version manager/container.
- Проверить workflow на PR с изменением shared interface и на documentation-only
  PR: первый запускает кодовые проверки, второй — только предусмотренные docs checks.
- Убедиться, что dry-run всех publishable пакетов проходит без dirty-tree warning.
