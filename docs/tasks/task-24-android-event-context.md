## Контекст

`TracerClient.recordError` объединяет постоянные ключи клиента и ключи одного
события в `packages/apptracer_flutter/lib/src/tracer_client.dart`. На Android
полученная карта целиком записывается через `Tracer.setCustomProperty` в
`AppTracerFlutterPlugin.recordError`. После `TracerCrashReport.report` прежнее
состояние нативных свойств не восстанавливается.

По коду есть риск, что одноразовый `customKeys` события A останется в глобальном
scope SDK и попадёт в событие B. Аналогично `dart.needs_symbolication` и
`dart.build_id` выставляются условно, но не очищаются для последующего события.
Это подтверждённый код-путь, но ещё не воспроизведённый на устройстве дефект.

Дополнительно нужно проверить фильтрацию: постоянные ключи заранее попадают в
native scope, поэтому удаление ключа из `TracerEvent` в `beforeSend` может не
удалить его из фактического Android-отчёта.

Основные места:

- `packages/apptracer_flutter/lib/src/tracer_client.dart:362`;
- `packages/apptracer_flutter_android/android/src/main/kotlin/ru/apptracer/flutter/AppTracerFlutterPlugin.kt:267`;
- `packages/apptracer_flutter_desktop/lib/src/event_mapping.dart:78` — пример
  намеренного восстановления отфильтрованных полей на desktop;
- `docs/privacy.md` — публичный контракт фильтрации и передаваемых данных.

## Цель

Гарантировать, что каждое Android-событие содержит только разрешённые для него
глобальные и одноразовые поля, без значений предыдущего события и без обхода
`beforeSend`.

## Сделать

1. Добавить воспроизводящий тест в существующий Android JVM/release harness:
   событие A с `endpoint=/orders`, затем событие B без `endpoint`. У B это поле
   должно отсутствовать. Постоянный ключ должен сохраниться на обоих событиях.
2. Проверить коллизию имён: одноразовое значение заменяет глобальное только для
   текущего события; следующее событие снова использует глобальное значение.
3. Проверить `beforeSend`, который удаляет или изменяет постоянный и одноразовый
   ключ. Сверять фактически сериализованный/принятый отчёт, а не только Dart model.
4. Проверить два последовательных события с разными `needsSymbolication` и
   `buildId`: диагностические поля первого не должны протекать во второе.
5. Выбрать минимальный механизм исправления после воспроизведения: отдельный
   per-event API SDK, либо снимок и восстановление native scope вокруг отправки.
   Не очищать постоянные ключи пользователя и не менять публичный Dart API.
6. Проверить поведение при исключении нативного SDK и при параллельных/быстрых
   последовательных `recordError`. Восстановление scope не должно смешивать два
   события или гонки с `setCustomKey`/`removeCustomKey`.
7. Зафиксировать отдельно результат аналогичного аудита iOS. Если дефект
   подтвердится там, описать его границы и связать исправление с этой задачей,
   не объявляя Android-проверку доказательством для iOS.
8. Обновить privacy/verification documentation по фактическому результату.

## Критерии приёмки

- Regression-тест воспроизводит проблему на исходной реализации и проходит после
  исправления.
- Событие B не содержит одноразовых ключей и diagnostic-полей события A.
- Постоянные ключи сохраняются, а их одноразовое переопределение не меняет
  последующие события.
- Удалённое через `beforeSend` значение отсутствует в фактически принятом отчёте.
- Сценарии ошибки SDK и последовательных отправок не оставляют частично
  восстановленный scope.
- Проверка выполнена на поддерживаемом Tracer Android SDK в release/R8; версии,
  тип приёмника и ограничения записаны в протокол.

## Проверки

- Существующие Android JVM unit-тесты и новые нативные regression-тесты.
- `./tool/check.sh` для общих Dart-регрессий.
- Release/R8 сценарий с loopback-приёмником либо тестовым проектом Tracer:
  проверить поля двух событий независимо и не записывать секреты в артефакты.
- `git status --short` после проверок: побочных изменений и отчётов с данными
  пользователя в репозитории быть не должно.
