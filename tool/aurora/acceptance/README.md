# Проверка нативного отчёта из песочницы Авроры

Тестовый RPM носит тот же app ID, что и пример плагина. Используйте отдельную
установку примера на эмуляторе. ADT при повторном развёртывании может удалить
данные предыдущей установки.

Подготовьте SDK по [инструкции пакета](../../../aurora/apptracer_flutter_aurora/README.md).
Из корня репозитория соберите тест с помощью Flutter Аврора. Параметр
`--sdk-dir` нужен при отдельной установке Build Tools. Скрипт собирает тестовую точку входа и платформенный пакет в новом каталоге
под `build/`. В конце Flutter выведет путь к подписанному RPM.

```sh
export AURORA_FLUTTER_BIN=/path/to/flutter_aurora/bin/flutter
tool/aurora/acceptance/build.sh --sdk-dir /path/to/AuroraSDK
adt device deploy --silent /path/to/test.rpm
```

Явно разрешите тестовый сбой и отправку двумя запусками. Каждая команда
запрашивает app token со скрытым вводом или читает `TRACER_AURORA_APP_TOKEN`
из окружения. Значение передаётся по SSH во временный файл с закрытыми правами.
Приложение считывает и удаляет его перед запуском рабочего процесса.
Имена переменных для запуска и символизации приведены в [шаблоне](env.example).
Параметры SSH ниже соответствуют локальному экземпляру эмулятора.

```sh
emu="$HOME/AuroraEmulator-5.2.1.200"
python3 tool/aurora/acceptance/run.py arm -- -p 2223 -i "$emu/ssh/id_rsa" \
  -o "UserKnownHostsFile=$emu/ssh/known_hosts" defaultuser@127.0.0.1
python3 tool/aurora/acceptance/run.py upload -- -p 2223 -i "$emu/ssh/id_rsa" \
  -o "UserKnownHostsFile=$emu/ssh/known_hosts" defaultuser@127.0.0.1
```

При первом запуске предоставьте тестовому приложению разрешение на сеть.
Команда `arm` включает нативный адаптер, записывает ключ и лог, затем вызывает
SIGABRT. `upload` восстанавливает согласованную сессию и ожидает завершения
попытки отправки. В кабинете проверьте NATIVE для версии `2.0.0 (202)`, ключ
`aurora_runner=consent-adapter` и лог «Разрешённое падение Flutter runner через
адаптер Авроры».

Для проверки жизненного цикла повторите команду запуска с указанными фазами
вместо `arm`. Во всех фазах работает платформенный пакет. Только тестовый RPM
умеет отключить сеть своего рабочего процесса или направить TCP-соединение SDK
на локальный сервер для управляемого отзыва.

| Последовательность | Что проверяется |
| --- | --- |
| `arm → offline → retry` | В первом перезапуске SDK получает ENETUNREACH, во втором обрабатывает очередь с тем же ID события. Проверьте число новых отчётов в кабинете. |
| `arm → hold → fresh` | Локальный сервер видит начало TLS-соединения. Отзыв завершает соединение, удаляет очередь и блокирует запись новых логов. |
| `arm → offline → switch → fresh` | Переход в аккаунт B и возврат в A очищают очередь A и обходятся без импорта предыдущего дампа. |
| `arm → cancel → fresh` | Отзыв между подготовкой и активацией старта отменяет отправку. |
| `revoke → fresh` | После подтверждённого отзыва тест вызывает SIGABRT. Следующий старт проходит без повторного импорта. |

Фаза `facade-dart` дополнительно запрашивает Sentry DSN того же проекта
(или читает `TRACER_AURORA_SENTRY_DSN`). Проверяются отложенный запуск,
большой Unicode-лог, удаление ключа и пользователя, исключение с исходным стеком
и HTTP-квитанция. В кабинете откройте последнее событие ERROR и найдите
`throwFacadeError` из `main.dart`. Фазы `facade-crash → facade-replay`
проверяют через общий API нативный SIGABRT сборки 203, ключ
`aurora_public_api=проверено` и лог «Контрольный шаг через публичный API».

Фаза `facade-lifecycle` использует HTTP-сервер внутри эмулятора. Сервер принимает
первый envelope и удерживает ответ. После `stopAndClearCollection` он проверяет
закрытие сокета. Следующий пользователь отправляет один envelope со своим ID и
ключом. Проверка отклоняет старый ID, лог или ключ, а также любую отправку до
согласия или после отзыва. Затем тест повторяет отложенный bootstrap, явно
включает сбор и дважды останавливает его.
